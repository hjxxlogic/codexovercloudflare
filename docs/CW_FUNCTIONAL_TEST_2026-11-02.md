## 缺陷与修复

### F1：历史引用释放未确认导致 ACK 风暴与恢复队列耗尽

线上真实新会话出现“历史确认队列已满，已停止自动恢复”。CDP 捕获另一独立观察浏览器收到超过 1300 条历史控制帧；数据确认水位已前进，releasedRevision 始终为 0，相同水位不断出现新 requestId。此时没有捕获到主线程 longtask，不能把所有卡顿归因于渲染。

根因：CW / CC 收到数据确认便清空 pending，而 commit 仍发现引用释放落后，立即生成新 ACK 并重置退避，形成请求循环。修改 apps/web/src/history-subscription.ts 和 native/src/history_subscription.cpp：协商引用释放后须同时确认两个水位，才完成待决 ACK；否则保留原身份与退避。

新增 TypeScript 和原生回归：连续 50 次仅数据确认不产生新 ACK，原请求继续重试，释放确认后停止。14 项历史订阅单测、全部 450 项 Vitest、9 项 CTest、网页构建、类型检查和界面回归通过。

复测分两种：线上原资源仍有问题；在独立测试浏览器拦截 JavaScript 资源、加载本机修复构建并连接真实线上接口后，约 147 秒只记录 14 条历史控制消息（含刷新重连），同一轮重试保持请求身份，没有确认队列满提示。此为本机前端与线上服务联调，不等于已部署修复；未验证线上为何未确认释放水位，不能宣称该服务端现象已消除。

探测脚本曾在模型保存尚未完成或文件下载尚未结束、dialog 仍打开时填写后台输入区，导致未输入和发送等待超时。确认并关闭 dialog 后恢复；不记为产品草稿丢失。

## 并行压力与用户反馈专项

三个独立浏览器上下文各自创建会话、屏障同步发送只读 Python 求和任务：仅 1/3 完成（24.05 秒），另外两会话 300 秒未出现输出，提示 signal timed out；三个会话均结束。按失败停止递增规则，未继续 5 并发，不宣称压力测试通过。第二轮 3 并发仍仅 1 个完成（29.85 秒），另两个 120 秒无输出。第三轮捕获可靠命令 delivery-result，明确两个失败结果均为 PROJECT_BUSY（Another session is executing in this project）；一会话 18.79 秒完成。说明同项目执行互斥是 Agent 的既有隔离策略，原脚本把预期拒绝误判为无限等待；后续独立查询超时覆盖过该业务提示。原三轮不据此改写为全部执行成功。没有放宽项目隔离。

历史缓存专项：IndexedDB 初始 184 条事件、8 页；首次打开较早页回源，之后为 226 条、9 页。同一页再次打开 61 毫秒，额外远端分页请求为 0。证明缓存存在且此次命中有效；不代表所有旧页均已缓存，不能据此否认首次加载或其它卡顿。

新增修复：底部滚动仅核对当前会话；刷新总等待上限 20 秒，超时恢复按钮；正常 AbortError（包括结束会话清理连接）不再显示 signal is aborted without reason，真实超时保留提示。此前收到 closing 后没有最终确认，现继续只读查询最多 60 秒，成功显示已结束，超时显示待确认。Agent 协商文案去掉误导的升级要求；未将瞬时协商错误等同版本不兼容，亦未宣称已消除所有协商失败。

本地回归：453 项 Vitest 通过，类型检查及网页构建通过；刷新截止时间、取消后不继续后续阶段、正常取消与真实超时区分有专项测试。新增真实 HTTP 快照挂起的 UI 注入，验证按钮有界恢复。
