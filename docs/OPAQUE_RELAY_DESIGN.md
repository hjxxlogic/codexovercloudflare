# 不透明中继架构设计（精简版）

状态：已实现并通过本机回归；尚未发布。基线：`589c26b`。实现与测试证据见 [验收记录](OPAQUE_RELAY_TEST_PLAN.md)；支持能力以 [项目需求](REQUIREMENTS.md)、[技术架构](ARCHITECTURE.md) 和 [用户手册](USER_GUIDE.md) 为准。

目标：**Worker 管理身份、权限和连接；Agent / Client 负责业务协议、控制权和可靠传输。Worker 知道谁可以连接谁、具有什么权限，看不到实际业务内容。** Client 包括现有 CLI/TUI、网页和可被远程管理的 CLI 进程。

## 1. 范围与取舍

本次覆盖现有功能，不增加产品能力。保留现有登录配对、API Key、Access 邮箱、角色和主机授权；保留现有命令、网页操作、平台支持、沙箱、审批与资源限制。业务加密是实现内容不可见目标所必需的新增传输能力。

不引入项目级 ACL、通用权限策略引擎、独立设备证书/带外配对、短期签名授权票据、周期续签或新客户端分发体系。也不新增离线消息存储、跨 Agent 锁或统一所有业务可靠性的框架。

信任 Worker 正确认证和管理权限，也信任现有网页及更新渠道。保密目标是让正常运行的中继只接触业务密文，不承诺抵抗 Worker 主动替换网页代码、身份绑定或密钥信息。Worker 仍可见身份、权限、连接双方、时间和流量大小；不隐藏通信关系。

## 2. 三方职责

```mermaid
flowchart LR
  C[Client：业务请求与本地恢复] <-->|加密业务| W[Worker：身份、权限、连接与转发]
  W <-->|加密业务| A[Agent：权限执行、控制权与业务执行]
  W -.->|可信连接身份及权限变更| A
  A --> S[现有 SQLite / Codex / 文件 / Terminal]
```

| 组件                              | 保留或承担的职责                                                                 | 移出的职责                                                           |
| --------------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| Worker / RegistryDO / HostRelayDO | 登录、角色、主机授权、管理员判定、撤销与到期、在线目录、唤醒、连接路由和有界转发 | 业务 HTTP 分发、会话租约与接管、项目写锁、业务 ticket、请求/结果关联 |
| Agent                             | 现有业务执行、持久状态、沙箱和审批；新增承接会话控制、项目写资格及业务路由       | 不维护第二套可独立授予权限的云端 ACL                                 |
| Client                            | 现有界面和命令、本地待办、结果与历史确认；通过加密通道直接调用端点业务           | 不再依赖 Worker 返回业务结果或仲裁接管                               |

**权限与控制权分开：** Worker 决定某身份是否有资格访问或管理主机；Agent 决定当前由哪个会话控制项目、是否可接管及何时执行。取得访问权限不等于取得当前控制权。

## 3. 权限：复用现有模型

Worker 继续使用现有凭据、邮箱关联及管理员规则。普通访问、项目管理和平台 owner 的远程配置权限仍按现有边界区分；不新增权限层级，当前没有项目级 ACL，重构后也不增加。

连接建立时，Worker 在已认证的 Agent 上行连接中发送绑定信息：当前连接标识、现有认证主体、目标主机、按现有规则计算的权限及有效期。Agent 只接受 Worker 控制消息中的身份，不能使用 Client 在业务正文中自报的 owner 或角色。绑定信息与本次加密握手关联，不能跨连接、主机或凭据复用。可被远程管理的 CLI 进程按相同方式接收管理者身份。

Agent 在解密后按照操作类型检查连接权限，并继续执行本地允许列表、沙箱与显式审批。Worker 无需知道本次请求的操作名称。普通业务帧不逐包查询云端授权存储。

撤销、邮箱及管理员变化继续使用现有持久失效事件和失败重试机制。Worker 停止失效连接转发，并通知端点退休对应连接；端点收到后拒绝该连接后续数据和未开始的派发。到期沿用原凭据期限，端点同时执行本地到期检查。上行断开或身份绑定丢失时，端点停止基于旧连接的新派发，重连后重新准入；不自动取消已经开始的任务。

权限变更的完成状态须包含端点失效确认；尚未确认仍沿用 `INVALIDATION_PENDING` 语义，不能把云端策略已修改描述为业务端已生效。失效事件与业务派发在端点串行处理，确认后旧连接不能再开始新操作；断网期间仍有检测延迟，不声称瞬时撤销。该确认只服务权限失效，不是业务持久 ACK。具体复用入口见 [Worker 连接授权](WORKER_CONNECTION_AUTHORIZATION.md)。

## 4. 业务：通过加密通道直接到端点

保留现有出站 WSS 拓扑，在 Agent 与 Client 之间增加端到端业务加密。两段终止于 Cloudflare 的 WSS 本身不能实现业务内容不可见。

只增加一个通用业务通道入口。外层携带协议版本、当前连接路由标识和不透明字节；Worker 检查大小、来源、目标与队列预算，不识别业务方法、sessionId、projectId、requestId、控制代际或正文。对同一对端的业务使用通道内消息区分，不按会话或 Terminal 在 Worker 新建业务路由。

端点握手和加密采用成熟协议与实现，要求支持 C++ 和浏览器、绑定本次 Worker 已认证身份、检测篡改及重放。密钥由端点生成，业务解密密钥不上传 Worker；Worker 可转发并绑定公开握手材料。重连重新建立安全连接，未决业务按原身份重新加密发送，不重放旧连接密文。实现使用原生 libsodium 与锁定的 `libsodium-wrappers 0.8.4`，复用 [crypto_kx](https://doc.libsodium.org/key_exchange) 的 X25519 会话密钥交换和 [secretstream](https://doc.libsodium.org/secret-key_cryptography/secretstream) 的 XChaCha20-Poly1305 有序认证加密。两方向使用独立密钥与 stream header，AAD 为 `coc-channel-1:hostId:link:authHash:role`。不生成设备长期私钥或证书。

外层 `/ws/v1/channel/:host?admin=1&target=agent|client-<hash>` 只接受 `channel-connect/key/header/data/close` 等连接封装；端点上行仍使用 `/ws/v1/agent` 与 `/ws/v1/client-management/:host`。客户端发送公开 key，Worker 生成 link 并绑定身份，端点交换公开 key/header 后才收发密文。连接建立前的路由错误可返回 `channel-error`，只含准入/目标离线信息。业务请求的 path、body、intent、请求号和逻辑流 ID 均加密。

通道密文单帧最大 256 KiB，明文按不破坏 UTF-8 的 64 KiB 分片；单逻辑消息上限 8 MiB。端点待开连接队列和 Worker 处理中队列同时限制字节及条数（8 MiB / 1024），原生端点最多 128 个待处理请求，每条连接最多 128 个逻辑流；浏览器每条通道最多 128 个待处理请求，Host 最多 256 条物理连接。浏览器检查 WebSocket bufferedAmount，原生复用有界发送队列。篡改、重复、乱序和旧连接密文使通道关闭；端点随后按原业务身份重建，不能跳过密文继续运行。

原 HTTP 业务方法迁入通道内请求/回复，现有 schema、requestId 和错误语义尽量复用。业务通知、大正文、文件、历史和 Terminal 都在通道内传输。主机业务能力、版本、会话摘要及远程配置路径也由端点加密返回；目录仅保留现有身份、主机名称、授权及在线路由所需信息。

登录、权限管理、在线目录、离线 URL 唤醒、公开下载与发布通知继续由 Worker 处理。这些是明确允许的控制面信息；具体任务、终端输入、配置内容和更新执行结果不进入明文控制面。保留现有网页交付与自动更新方式，不另建发布签名体系。

### 现有功能对应

| 现有功能                                            | 重构后的处理                                          |
| --------------------------------------------------- | ----------------------------------------------------- |
| CLI RPC / TUI，网页任务、模型选择、审批、停止和接管 | 端点业务消息；Agent 执行并管理会话                    |
| 项目列表、目录浏览、添加、改名和取消注册            | Worker 提供现有项目管理权限；Agent 检查权限并操作     |
| 邮箱归属会话列表与续接                              | Agent 根据 Worker 绑定的现有用户身份过滤和返回        |
| 历史、外部 Codex 观察/入队/审批                     | 保留现有 Agent 策略与订阅语义，传输改为加密           |
| 文件树、预览、上传下载、工作台                      | 复用现有业务与路径校验，不改变界面能力                |
| Linux Terminal                                      | 保留启用条件、隔离、字节流、确认、背压及恢复限制      |
| Agent / 在线 CLI 配置读取、替换与显式重启           | 现有 owner 权限；目标进程通过加密通道处理并保存原回执 |

可被管理的 CLI 沿用现有在线进程身份和生命周期，不增加常驻服务或任意端点互联能力。离线时显示本地已保存内容及其陈旧状态，不新增云端业务缓存。

## 5. 控制权：从 HostRelayDO 移到 Agent

迁移现有租约、`controlEpoch / controlId / owner`、接管中的旧端屏障、项目单写资格及控制恢复逻辑，存入 Agent SQLite。Worker 只保留连接状态，不保存会话控制状态，也不签发业务 ticket。

接管流程保持现有语义：Agent 校验 Worker 给出的权限，在本地事务中更新控制代际、阻止旧端新派发，然后返回 `CONTROL_READY`。Client 收到匹配的控制确认及恢复快照后才能发新命令。接管、撤销和 `received → started` 派发在 Agent 串行处理，不能让旧代际越过执行边界。

接管重试沿原 requestId 查询，不重复增加代际；普通断线恢复只变更连接，不改变控制权。项目预留只覆盖尚未使用的一次性 ticket；已连接控制端断开后释放项目写资格，不等待 ticket 截止。已有任务的真实状态、项目单写、Terminal 与模型任务互斥、多标签页协调及 dataDir 独占锁均保留。接管成功不代表旧任务已停止；Agent 离线时不能完成接管。

## 6. 可靠性：复用现有实现

复用 [delivery:2](RELIABLE_TRANSPORT.md)、原请求回执、历史订阅和 Terminal 的现有语义。重构只替换传输与权限/控制来源，不统一重写这些机制：

- Client 先保存原请求，Agent 先保存接收/执行状态和终态，Client 落盘后确认；保持去重、信用、保留期限及清理后的拒绝屏障。
- 断线沿原身份恢复；未知结果不自动换编号重做；配置写入/重启继续使用现有专用回执。
- 历史订阅独立确认，文件及大正文继续分块校验；Terminal 保持易失输入输出、渲染确认和未知按键不重放。
- Worker 只有有界临时转发队列；连接中按序转发，队列满或映射无法恢复时关闭对应连接，不静默丢弃中间字节，不提供业务 ACK 或回放。

保留现有条数、字节、进程及存储预算，增加加密开销计量。端点在发送前分块和调度，防止文件传输堵住取消、恢复或 Terminal。DO 重建可以要求端点重连，业务恢复不依赖 Worker 临时状态。

## 7. 最小实施顺序

| 步骤          | 工作                                                                    | 验收条件                                                                 |
| ------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| 1. 通道互通   | 基于现有认证建立 C++ / 网页加密通道；传递可信身份和权限失效通知         | Worker 只见密文；错绑、断线、撤销与到期正确处理                          |
| 2. 迁移职责   | 将会话控制和业务路由迁到 Agent / Client，覆盖上表全部现有功能           | 现有功能测试通过；权限、接管和可靠交付语义不退化                         |
| 3. 删除旧路径 | 移除 Worker 业务 API、schema 依赖、租约和请求关联；保留权限与运维控制面 | Worker 无业务解密密钥、正文或会话状态；新增同权限业务方法无需修改 Worker |

优先调整现有 `index.ts / host.ts / registry.ts`、原生传输与业务模块、网页 `api.ts` 及现有流处理代码。只抽出中继与端点必须区分的协议边界，不预设新包数量或通用框架。

切换按 Agent 为单位：等待活动工作结束、核对未决请求、备份状态，再切到新的控制权来源。同一 Agent 不同时接受两套控制仲裁；保留凭据、配置、项目和历史，不把旧未决请求自动变成新请求。旧客户端明确提示升级，不静默回退明文业务。

回退先停止新写入并保留账本，确认无活跃副作用；旧程序不能直接读取不兼容状态或重放已经执行的请求。精确状态迁移随实现确定，不在本轮新增迁移工具。发布仍遵循现有精确提交 CI、验证制品和部署脚本要求。

## 8. 验证边界

完整用例、现有覆盖对应与执行状态见 [设计测试与验收](OPAQUE_RELAY_TEST_PLAN.md)。

复用现有认证、隔离、审批、去重、控制接管、重连、文件、历史、配置及 Terminal 测试。仅补充架构变化引入的检查：

- 抓取 Worker 流量、DO 状态和日志：允许连接/权限/运维元数据，不能出现业务正文、实际操作方法或会话控制状态。
- 跨身份/主机错绑、密文篡改、退休连接晚到数据：拒绝业务派发；权限失效确认不早于端点执行屏障。
- 并发接管、确认丢失、Agent/DO 重启：旧代际不能新执行，原请求不重复执行，未知结果如实返回。
- 大文件与交互并发、队列满及存储失败：资源有界，不虚报业务成功。

设计对应实现和本地验收已完成，具体结果与限制见 [设计测试与验收](OPAQUE_RELAY_TEST_PLAN.md)。线上发布独立记录，不能由本地测试结果推断已部署。
