## 7. `r.xlogic.cc` 平滑切换方案

### 7.1 升级原则

优先使用现有自动更新，无法自动更新时允许通过仓库部署脚本或官方 CI 包手动更新 `coc-agent`。不要求所有旧进程均能自动发现新版，也不为此建设旧业务兼容、专用引导版本或下载预发布系统。自动更新失败不能绕过制品身份和摘要检查；手动更新使用同一已验证发布的制品。

新版 Agent 必须兼容旧版数据库；允许一次性、单向自动迁移，不要求旧 Agent 反向读取升级后的数据库。无论自动或手动更新，都保留配置、凭据、dataDir、主机身份、项目及历史，不以删库、重新配对或重新初始化作为正常升级步骤。新版 Worker 无需支持旧 Agent 业务协议，短暂切换窗口和未更新实例的升级提示可以接受。

### 7.2 新 Agent 对旧数据库的兼容

1. **列出实际旧格式。** 发布前确认生产待升级版本及数据库 schema；以这些版本实际创建的库作为测试输入，覆盖现有主分支及受支持的历史格式。源分支目前接受结构完整的 SQLite `user_version=0/1/2` 并升级到 2，但仅版本号匹配不足以证明兼容。若实际旧库缺少新版要求的表或列，应补充明确迁移，而非直接判成不支持或要求清库。
2. **保留全部业务账本。** 核对会话、历史正文与索引、消息队列、项目关联、请求接收/执行/终态、确认水位、去重和过期拒绝屏障；新增端点控制状态不得使旧请求重新变成可执行的新请求。项目登记文件和配置也需保全，不能用初始化配置覆盖已登记项目。
3. **事务与恢复。** 获取 dataDir 独占锁，建立一致性备份，校验旧结构后按版本执行迁移；结构变更、数据转换和版本标记在事务内提交，较大迁移需有持久进度与恢复设计。备份须包含已提交 WAL 内容，不能只复制正在写入的 SQLite 主文件。失败保留可恢复旧状态；再次启动可继续或安全重试，不重复插入、不丢记录。
4. **兼容性验收。** 用新版打开真实旧版生成的含数据测试库，验证关键记录、业务查询和恢复语义，随后再次重启验证幂等；注入写入失败、中途退出及磁盘不足。未知未来格式或损坏库明确报错并保留数据，不进行猜测性修复。生产数据副本和原始日志只留在私有忽略路径。

### 7.3 线上 DO 一次性迁移

允许对现有生产 DO 存储执行一次性迁移，继续使用现有 namespace 与对象身份，不通过新建空 namespace 规避数据兼容。迁移实现、入口和验证纳入仓库代码/部署脚本及同一 CI 审查。

- **先定义映射。** 分别清点 RegistryDO 和 HostRelayDO 的旧键、值结构、alarm、WebSocket attachment 及迁移标记；列明保留、转换、迁往 Agent、作废和删除的规则。身份、主机目录、授权、撤销/到期、待完成权限失效与必要唤醒状态必须保全，不能因迁移扩大权限。
- **处理控制权归属。** 旧租约、ticket、项目写锁和业务路由迁出 Worker。确认活动工作结束，核对 Agent 账本及未决请求后，再按规则退休旧控制状态；必要的未决信息须先可靠交接并确认，不能一律删除。新 Agent 按可信身份重新建立控制权，旧连接和旧代际不得恢复写资格。
- **修订现有清理逻辑。** 源分支 HostRelayDO 的 `channelVersion` 初始化路径目前分页清空存储，仅暂存并恢复 `wakeUntil`。这不能直接视为生产迁移已满足要求：必须逐键审核保留集合，尤其是权限失效进度；`wakeUntil` 不能只存在于进程内，否则删除后中断会丢失。迁移备份和进度不得被后续清理批次误删。
- **一次语义、可重复执行。** 为每个对象设置迁移版本、阶段和游标；单对象使用事务或适合其大小的可续跑批次，完成校验后才写完成标记。并发请求、重启和重复调用不得重复迁移；迁移期间阻止业务写入，权限校验保持失败关闭。处理旧连接附件及 alarm，使它们不能绕过新状态。跨 DO 不假设全局事务，脚本记录逐对象结果和失败重试。
- **备份与覆盖。** 写入前保存可恢复快照并验证读回；在部署窗口控制并发，明确全量枚举或首次访问懒迁移策略。若使用懒迁移，离线主机对应 DO 日后首次访问也必须先完成迁移，不能将未访问对象记录成已迁移。公开文档仅记录摘要与结果，不包含凭据或私有状态。

### 7.4 发布顺序

1. **准备制品与演练。** 等待最终准确提交全部必需 CI 成功，核对 Worker、Web 和原生包来源与摘要；完成旧数据库兼容、DO 迁移以及自动/手动安装后的业务恢复演练。r2 可用于隔离验证，最终目标为 `r.xlogic.cc`。
2. **生产预检和备份。** 记录当前部署、下载及范围内 Agent 身份，备份 DO、Agent 数据库和相关配置/项目登记。暂停新任务准入，等待任务、队列执行、Terminal、读取和文件操作结束；不将单次空闲快照当成原子屏障，不默认强制重启活动会话。
3. **部署云端并迁移 DO。** 通过 `scripts/deploy-cloud.py` 发布 CI 验证的 Worker/Web 及原生下载，按既定入口执行 DO 一次性迁移；若采用首次访问迁移，先对本次验收对象触发并核验。保留生产 Access、Secret、路由和 namespace。下载清单和包验证通过后可发送现有更新通知，通知不代表安装完成。
4. **升级 Agent。** 可自动更新的实例等待空闲安装；无法自动更新、漏通知、脏构建或不支持自动替换的平台，按已验证的手动流程安装同一发布制品。Linux systemd 场景使用 `scripts/deploy-agent.py --push` 及适用目标参数，正常等待空闲；Windows 按既有完整包替换流程操作。只补齐必要脚本能力，不要求旧更新器接受不兼容清单，也不假报自动更新成功。
5. **保留状态并恢复。** 新 Agent 以原配置和 dataDir 启动，完成必要数据库迁移，连接原域名。刷新 Web，核对 CLI 版本及恢复状态；明确提示仍未更新的实例需要升级，不支持旧业务协议回退。离线实例以后也可自动或手动升级，连接前完成本地及对应 DO 迁移。
6. **验收并开放业务。** 核对云端和范围内 Agent 的实际版本、制品身份、数据库/DO 迁移状态以及加密业务、队列、历史、权限和文件操作。确认原请求未重复执行、数据未丢失后恢复准入。记录升级方式、失败与待升级实例、尚未访问的 DO；不得将这些对象记为已验收。

### 7.5 失败与回退

云端部署、DO 迁移和 Agent 安装分别记录检查点与结果。迁移失败时关闭受影响对象的新业务，保留快照和进度后重试或修复，不通过清空状态继续。已升级数据库与旧二进制不一定兼容，已迁移 DO 也不能直接交给旧 Worker 使用。

优先使用兼容新状态的 CI 制品向前修复。确需回退时先停止新写入，保存当前账本并核对升级后副作用，再按经过演练的组件和状态恢复方案操作；恢复旧快照不能丢弃新执行记录或导致副作用重放。回退是独立恢复流程，不要求在新业务内保留旧 Agent 协议。
