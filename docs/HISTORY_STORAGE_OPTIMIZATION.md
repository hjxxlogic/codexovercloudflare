# 历史存储、环形缓存与 JSON 配额优化方案

[文档索引](README.md) · [现行资源盘点](TRANSPORT_STATE_INVENTORY.md) · [发布记录](DEPLOYMENT_STATUS.md)

状态：**按批实施中，尚未发布**。调查日期 2026-11-01；运行源码 `4b164c6`（0.6.0），文档基线 `bfa927a`；本机 Codex 0.166.0，仓库此前验证基线为 0.164.0。下文是完整目标；仅第 11 节列出的开发实现已完成，其余设计不能直接写入现网配置期待生效。

## 1. 结论与决策

核心保留原则：**Agent 只持久保留尚未解除的可靠性责任，以及无法从 Codex 恢复的必要证据；已由 Codex 可靠保存、可按原身份和内容校验重读的历史正文只做有界缓存。** “只保存与客户端未决的消息”适用于交付正文的主要保留条件，不能作为整个持久库的删除规则。

采用“Codex 历史回源 + Agent 有界正文缓存 + 独立可靠性账本”。缓存可以按环形/FIFO 方式淘汰已满足回收条件的条目；不能把当前整个 Agent 历史库当作环形缓冲区直接覆盖。

用户要求：**实现中的历史资源限制必须可在 Agent JSON 文件配置**。默认值、解析校验、Store 执行、诊断展示使用同一个规范化策略；不再让 C++ 常量、SQLite 触发器和 TypeScript 各维护一套实际额度。该要求不意味着允许修改线上协议帧安全上限或放开无限增长。

先修复容量不足的准入与故障隔离，再去重和引入回源，最后启用安全淘汰。恢复不一致按第 4.4 节区分可接受变换、新修订及必要快照，优先扩大可恢复范围，不一律拒绝所有差异。无法证明可恢复的数据继续保留并占用预算；容量不足时拒绝新承诺，不删除必要证据，也不让 Worker 接管交付。

### 1.1 实现语言与职责边界

**Agent 历史优化的核心实现全部使用 C++。** JSON 是配置文件格式，不是 TypeScript 运行依赖。正文存储与合并、SQLite 迁移、预算执行与预留、Codex 回源、淘汰选择、可靠性证据保留和故障恢复均在 `native/src/`、`native/include/coc/` 实现；原生 CC 的适配也使用 C++。不引入 Node.js 服务或脚本承接这些运行职责。

方案中的 TypeScript 文件仅有以下配套用途：

| 用途          | 允许改动的范围                                                                                                   | 不承担的职责                                              |
| ------------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- |
| 配置/协议定义 | `packages/protocol/src/index.ts` 同步已有 `agentConfigSchema` 的 JSON 字段、类型、默认值及边界，使用共享校验样例 | 不保存 Agent 的实际占用，不计算或授予运行信用，不执行淘汰 |
| CW 网页适配   | 仅在新增历史缺口、快照恢复或引用读取语义时，调整网页消费协议的逻辑                                               | 不实现 Agent 的存储、Codex 回源或第二套可靠交付引擎       |
| 集成测试      | TypeScript 测试驱动真实 C++ Agent/CC、Worker 和浏览器，注入故障并验证结果                                        | 不以 TypeScript 模拟实现替代被测 C++ 核心                 |

如果优化只涉及 Agent 内部缓存，并保持现有接口、历史引用和游标语义不变，则不修改 CW 运行逻辑。需要新增缺口恢复语义时，先证明必要性并明确协议变更，再同步适配 C++ CC 和 TypeScript CW；不能为“统一实现”扩大网页或 Worker 的业务职责。Worker 继续只承担授权、路由和有界背压，不接管历史可靠存储。

## 2. 本机故障与只读测量

Agent 原配置的代理出现网络错误；临时直连能完成握手、项目/会话列表与历史读取。其后收到真实创建请求，触发 `COC_HISTORY_CAPACITY`，返回 `RESULT_UNKNOWN` 并停止 Agent。网络故障与容量故障是两个问题，本文仅处理后者。不重发该创建请求，不把未知状态推断为未创建。

对启动前 SQLite 在线备份只读统计：

| 记账对象 |   条数 |    预算字节 |
| -------- | -----: | ----------: |
| events   | 48,224 | 147,325,641 |
| chunks   | 40,163 | 104,311,385 |
| history  |  8,416 |  35,819,922 |
| bodies   |    355 |     911,894 |
| streams  |     51 |     194,559 |
| 合计     | 97,209 | 288,563,401 |

总计约 275.2 MiB，高于全局 256 MiB；最大单会话约 67.5 MiB，高于单会话 64 MiB。备份文件实际为 67,444,736 字节（约 64.3 MiB），数据库完整性正常。这是预算记账，不是 Cloudflare 费用、内存 RSS 或实际文件占用。

[history_budget.cpp](../native/src/history_budget.cpp) 的公式是：正文 UTF-8 字节数 + 每条 2048 字节 + 6 倍记账键字节数 + 6 倍 session 标识字节数。多个物理副本分别计量。固定开销一项就约 189.9 MiB；不能把 275.2 MiB 全当作重复聊天正文，也不能通过只减小记账数字宣称已减少磁盘。

样本含 31 个非 external 的 web 会话；本机超限并不只发生在外部会话镜像。既有数据初始化后才安装限额触发器，因此旧数据超限仍可读取，但新增记录会被拒绝。[公开聚合证据](assets/history-storage-2026-11-01/investigation.json) 不含正文、凭据、会话或项目身份。原始诊断和备份只保留在忽略目录 `.local/agent-live-test/`。

## 3. 历史究竟从哪里读取

### 3.1 现有 Agent 路径

| 路径            | 当前实现与后果                                                                                                                                                      |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 实时 Codex 通知 | Agent `on_codex` 等路径调用 Store，`event_batch` 在同一事务插入 events 并投影为 history；增量输出还写 bodies/chunks                                                 |
| 外部只读会话    | [external.cpp](../native/src/external.cpp) 通过 app-server 分页、追踪当前 turn；`Store::external_item` 将变化再写入本地 events/history/chunks，并记录 fingerprint   |
| 加载更早历史    | Agent `read_archive` 调用 `thread/items/list` 或 `thread/turns/list`，经 `external_item` / `archive_page` 持久复制到 Agent SQLite；不是直接透传页面                 |
| 网页历史及正文  | `Store::history` / `content` 读取 Agent 本地投影和分块；当前并不在缓存缺失时透明回源                                                                                |
| history 引用    | [history_reference.cpp](../native/src/history_reference.cpp) 保存 Agent instance、session、seq、revision、长度及 SHA256；读取仍依赖 Agent SQLite，不是 Codex 定位符 |
| 清理            | `Store::cleanup` 只回收指定过期上传缓存，不自动清理上述权威历史；结果 ACK 不删除历史                                                                                |

[store.cpp](../native/src/store.cpp) 保留原始增量事件，同时形成合并投影；较小投影还内联正文，分块又保存正文。外部条目替换会退还旧 chunks 容量，但原始变更事件继续保留。因此正文复制和细粒度记录开销都有优化空间。

### 3.2 本机 Codex 的真实存储与接口

只读检查本机数据库结构发现：

- `state_5.sqlite` 的 `threads` 保存线程元数据、`rollout_path` 和 `history_mode` 等，不是唯一正文来源。
- `thread_history_1.sqlite` 有 `thread_turns`、`thread_items`、`thread_realtime_items`、`thread_history_projection_state`；`thread_items.item_json` 确实保存条目正文。投影表同时保留 rollout 偏移/序号信息。
- 从已安装 Codex 生成的 app-server schema 显示，`thread/read(includeTurns=true)` 的全量历史加载对 paginated 线程已不推荐，应使用分页接口。
- `thread/items/read` 可按 thread、turn、1–100 个 item ID 读取持久化条目，但标记为 experimental。分页游标为 opaque；接口没有承诺可读取指定旧 revision 或按旧摘要寻址。

启动独立 app-server，只执行 initialize、元数据 read、单条 items/list 和 items/read，四项成功；没有 start/resume/turn、模型调用或内容输出。该探测证明**一个已完成条目可按身份读取**，不证明完整历史等价性、进程重启后的所有游标有效性、0.164.0 接口覆盖或旧修订可重建。

优先使用 app-server API，不直接依赖 Codex 私有 SQLite 表作为运行协议；数据库结构只用于本次调查。不得绕过项目路径、用户、实例及 thread 归属校验。回源进程只能读取，不能用 `thread/resume` 或 `turn/start` 冒充读取。

### 3.3 不能推导的结论

Codex 最终 item 不等于每条流式 delta，也不一定等于 Agent 脱敏、投影后的正文；计划最终项甚至可能不同于 delta 拼接。Agent 生成的会话状态、请求回执、审批绑定及协议证据也不由 Codex 全部保存。

因此“历史来自 Codex”只证明部分内容可重读，不能证明任意 Agent seq/revision 可重建。必须逐类建立标准化投影及身份映射，比较摘要后才能允许淘汰副本。对于已返回的不可变引用，禁止把最新 item 偷换成原 revision。

## 4. 状态分类与回收条件

| 类别           | 典型数据                                                                                      | 策略                                                                   |
| -------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 必要可靠性状态 | 原请求身份/摘要、执行状态、结果、sessionId 关联、控制代际、实例、ACK/信用承诺、未确认 outputs | 不进入历史环形缓存；保持现有事务和退休条件，未知结果不得按 TTL 清除    |
| 必要正文快照   | 无法精确回源的输出、已承诺保留的引用版本、未安全确认的正文                                    | 在有界持久区固定；预算不足先拒绝新增承诺，不能覆盖                     |
| 可重建正文缓存 | 已验证 Codex 来源、投影版本和摘要的历史条目/页面                                              | 可按分段 FIFO 淘汰；读取缺失时回源并校验，再按预算决定是否缓存         |
| 派生索引/统计  | 正文长度/摘要、缓存计量、定位索引                                                             | 有界保存；能重建不等于每次启动都全量扫描；与正文变动事务一致           |
| Agent 独有历史 | 无 Codex 等价物的告警、状态事件等                                                             | 分别判定业务证据或展示数据；前者保留，后者只有明确的保留契约后才能淘汰 |

普通结果 ACK 只证明客户端已持久保存终态/描述符，不代表 history 正文可以删除；现有测试已明确这一点。`CONTENT_UNAVAILABLE` 是真实源缺失/旧修订不可恢复的边界，不得用它掩盖自动淘汰引入的新丢失。没有回源保证的旧引用保持固定，或经明确的离线归档策略处理；本轮不默认降低既有可读性。

### 4.1 正文、执行证据和展示缓存的责任分离

| 对象         | 保留到何时                                                                                     | 不能作为回收依据的情况                                             |
| ------------ | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 交付正文     | 客户端持久确认完整正文，或已验证的可靠来源能够按原版本精确恢复；同时不存在其它未解除的保留承诺 | WebSocket 发送成功、客户端仅收到内存、仅确认引用、页面关闭         |
| 请求执行证据 | 原请求仍可能重试/查询、执行结果未知或控制流尚未安全退休时继续保留                              | 没有待发送消息、网络断开、客户端卸载、普通缓存 TTL 到期            |
| 历史展示缓存 | 可按预算淘汰；后续按授权从 Codex 重读                                                          | 未验证回源等价性、把最新条目当作旧修订、假定所有流式通知都已持久化 |

“消息不再待交付”和“操作已安全完成”不是同一事实。客户端断开不会取消执行中的请求；Codex 已生成内容也不证明该内容已经持久化或与 Agent 脱敏后的正文一致。副作用尚未知时继续保存原身份和恢复证据，不通过重新执行来补全历史。

### 4.2 ACK 具体解除哪一层责任

- **完整正文的持久 ACK：** 接收端已将所承诺的完整正文及接收检查点原子落盘。发送端持久记录有效 ACK 后，可以回收对应交付副本，但仍须满足其它接收者、历史引用及查询的保留承诺。客户端后续清理展示缓存不能重新开启原请求。
- **结果描述符/历史引用的持久 ACK：** 只确认终态和引用已保存，不确认正文已取得。当前 history 引用采用该语义；必须先落实引用指向的持久正文或可校验的可靠回源，不能据此直接清正文。
- **业务操作的确认：** 可按现有规则回收结果正文，不意味着原请求从未存在。去重证据、创建 requestId 到 sessionId 的查询关联以及实例/控制代际边界不能随正文一并回收。

逐类记录每种 ACK 的确认对象、持久事务和允许回收的资源，复用现有确认机制；不为统一命名再增加一套 ACK。多客户端/多标签页按实际交付和保留承诺判断，不能拿某一个客户端的 ACK 代表全部接收方。

### 4.3 必要证据有界压缩，不永久逐条堆积

已完成请求的正文可以释放；必要身份可在协议允许的安全边界压缩为连续确认边界、流关闭检查点或代际退休证据。压缩前必须证明：迟到旧请求会命中原结果/查询关联，或明确拒绝为已退休请求，绝不会被当作新请求执行；拒绝也不能破坏仍承诺提供的原请求结果及 sessionId 查询。

检查点与逐条证据删除同事务提交，崩溃恢复后必须保留等价的拒绝与查询能力。控制代际、Agent 存储实例和主体约束继续有效；仍有未知结果、缺口或未兑现承诺时不能推进退休边界。达到身份容量上限时停止新增承诺，不用 TTL 或环形覆盖释放去重身份。优先复用现有流退休机制，不新增永久重复账本。

### 4.4 恢复不一致的可接受边界：优先恢复，不将所有差异一律判失败

按用户补充要求，首先判断差异是否影响当前读取承诺。**原引用正文、普通最新历史、业务执行结果是不同对象**：回源只能读取和重建，不据此重执行业务，也不能把未知操作改成成功。

| 差异 | 可接受方式 | 不可越过的边界 |
| --- | --- | --- |
| Codex 持久条目新增生产时间字段，原实时事件没有 | 按已保存的原字段形态去掉新增 `startedAtMs` / `completedAtMs`，再验证原长度和 SHA-256 | 原历史本来含有的时间字段不能随意丢弃或改写 |
| 不影响正文视图的附加元数据变化 | 复用相同版本的正文投影，正文摘要一致即可恢复；不要求整个源 item 指纹相等 | 不把新元数据伪装为旧事件；身份、授权仍独立校验 |
| 后续输出追加，原正文是当前正文的前缀 | 按原 UTF-8 字节长度截取，验证原摘要；通过后可恢复旧正文 | 不以“看起来相似”代替摘要，不混淆字符 offset 与字节长度 |
| 原命令流只覆盖完整输出中的一个片段 | 本地原文还在时注册可验证的来源字节偏移；以后按偏移/长度截取并验证旧摘要 | 偏移要计入来源元数据并持久化；偏移不是权限证明；错位必须失败 |
| started → completed、正文实质修改 | 普通“最新历史”可使用新完整投影及新 revision；明确刷新或返回 `CONTENT_CHANGED` | 不能向旧引用返回新正文，也不能把完整快照作为 delta 重复追加 |
| Codex 输出已截短、原条目缺失 | 保留必要本地快照；普通最新视图可明确说明来源缺失 | 不拼造丢失部分，不因少数不可恢复条目禁用其它条目的回源 |
| 项目/来源/身份改变或权限撤销 | 拒绝读取并保留原本地责任 | 不能通过内容相似绕过权限或来源校验 |

对仅剩小型开始态的记录，优先保留必要状态元数据，而不是因此长期固定同条目的全部完成正文。对已有旧引用继续遵守原 revision/内容校验与明确失效语义；不额外宣称所有历史修订永远可查询。最新视图替换、元数据固定及缓存淘汰须在来源映射、事务和客户端恢复路径接通后启用；本批只接入投影与验证基础。

## 5. 推荐存储与环形缓存模型

### 5.1 先复用现有库，避免新增框架

仍使用 SQLite；在现有 history/bodies/chunks 基础上逐步消除重复正文。新增字段或表须在实现前给出“读写者、必要性、恢复、回收”清单，不创建第二个业务请求账本。逻辑分为可靠性账本、必要历史快照、可重建缓存；可以同库事务，不能因缓存清理连带删除必要数据。

来源描述至少区分 Codex 用户环境/来源实例、项目与 thread、turn、item、投影格式版本及内容摘要。路径不能作为授权；环境重绑或同 ID 不同来源必须拒绝。摘要只代表字节身份，不能独自恢复正文。定位元数据也计费，不允许正文有界但定位表无限增长。

### 5.2 采用可跳过固定条目的分段 FIFO

“环形”是有界保留策略，不复用公开 seq 数值或覆盖任意槽位。按会话组织缓存块，全局 FIFO 回收可重建、未被读取事务占用的块；同时满足全局和单会话额度。活跃块先封存再回收；固定内容不能被后续写入覆盖。避免每次读取都持久更新 LRU 时间，降低 SQLite 写放大。

淘汰与记账扣减同事务提交。若回收候选不足，读取可有界直出而不落缓存；新增必要正文必须背压。读取中的短期固定有超时/并发上限；超时只结束读取租约，不释放业务可靠性固定。

### 5.3 回源和序列语义是启用淘汰的前置条件

1. 先读本地正文；缺失时校验权限、来源及稳定身份，再发只读 Codex API。
2. 使用固定版本的脱敏/标准化规则投影，验证长度、摘要；不可将协议字符 offset 当 UTF-8 字节偏移。
3. 不一致返回内容变更/不可用；来源暂不可达返回可重试读取错误，不删除待办、不执行业务。
4. 用固定大小正文块合并小 delta，减少 chunks 数目；尾部追加、正文身份、修订和容量在同一事务维护。先覆盖 Unicode、随机 offset 和崩溃测试，再清除冗余副本。
5. 当前 `snapshotSeq` 来自 events 的 `MAX(seq)`，向后历史还使用负 seq，向前增量使用 revision。删除事件会影响高水位及断点恢复，不能直接执行 `DELETE ... LIMIT`。
6. 必须在回收前持久提交单调历史高水位、可用增量下界和快照身份；为落后订阅者提供有界快照重同步。客户端先保存快照/检查点再 ACK，不能把缺口当成已交付。
7. 若需要新增缺口/快照语义，明确协商能力或升级业务协议版本；不能偷偷改变 delivery:2 的 cursor 含义。CC、CW、多标签页和 HTTP/WS 都必须理解后才启用事件淘汰。

已完成 Codex item 的按 ID 回源是首选；不支持该能力的版本保持有限分页检索和保留策略，查找预算耗尽明确失败，不能无限扫描或默默切到直接读私有数据库。只支持实际需要的来源能力，不增加业务协议降级路径。

## 6. JSON 配置契约（拟实施）

配置位置：Agent 现有 `agent.json`。以下是**提议默认值**，不是本机修改指令；第一批兼容原配额，不自动增大容量。所有容量单位为字节，计数为条，比例为整数百分比。

```json
{
  "historyStorage": {
    "maxBytes": 268435456,
    "maxSessionBytes": 67108864,
    "maxRecords": 250000,
    "maxSessionRecords": 64000,
    "maxSessions": 1024,
    "cacheMaxBytes": 67108864,
    "cacheMaxSessionBytes": 16777216,
    "cacheTargetPercent": 80,
    "readPageMaxBytes": 1048576,
    "readConcurrency": 2,
    "minFreeDiskBytes": 536870912
  }
}
```

- `max*` 是本 Agent 历史域总预算，**包含必要快照、缓存、定位元数据及未兑现的历史写入预留**；cache 额度是子集，不能加到总额度外。现有可靠操作/传输的预算仍独立计量并受总体资源规则约束，不能从历史缓存借出已承诺信用。
- cache 配额只在缓存实现完成后开放；P1 只接受已实现字段，未知字段报错，防止“设置成功但无效”。`cacheMaxBytes=0` 表示不保存可重建缓存；`maxBytes=0` 不表示无限，应拒绝。其它必要额度必须为正。
- C++ `agent_config` 与 TypeScript `agentConfigSchema` 使用共享边界样例；拒绝负数、小数、非数值、溢出及相互矛盾设置。所有整数不超过 JS 安全整数和 SQLite 整数范围，资源相加用溢出检查。实现时给并发数明确安全上限（提议 1–16），超限报错而非静默夹紧。
- `maxSessionBytes <= maxBytes`、`cacheMaxSessionBytes <= cacheMaxBytes <= maxBytes` 且不超过对应 session 上限；记录数同理。`readPageMaxBytes` 不得超过现有单次读取/帧分块安全限制；较大内容分页，不能随配置放大 wire frame。
- 第一版配置重启生效；远程配置替换和重启沿用现有 revision/备份/原请求回执流程，不额外实现热更新状态机。客户端不独立推导或授予信用。
- 上调不自动重放被拒请求，不把历史 `RESULT_UNKNOWN` 改成可重试；下调不删除必要数据或撤销已授信用。允许以“占用高于配置、限制新增”的状态启动，doctor 必须指出范围、缺口及处置方式；恢复到预算内再接收新承诺。
- 本机有全局与单会话两个超限点，只提高一个仍可能失败。是否采用更高额度须由操作者决定，本文不建议通过无限额度掩盖复制问题。
- `minFreeDiskBytes` 是提前拒绝新承诺的磁盘余量门槛，不是原子保证。还必须处理 WAL、并发进程写盘及真实 SQLITE_FULL；低磁盘不得自动删除账本或快照。

### 配额权威及触发器迁移

现有 `CREATE TRIGGER IF NOT EXISTS` 将编译期常量写进触发器；仅修改 `credit.hpp` 或解析 JSON 不会更新已有库触发器。必须迁移为读取唯一运行策略的校验方式：建议在独占 Agent 实例锁下，事务安装版本化触发器与单行有效配额，Store 与触发器引用同一规范化值。该单行是 JSON 的可恢复执行投影，不是第二份可独立修改的配置。

解析失败在写库/启动 Codex 前终止；迁移失败整笔回滚；崩溃后从有效 JSON 重新应用并验证策略。记录 layout/accounting 版本，禁止旧二进制接管不认识的新布局。限制与记账公式的变更分开迁移，不靠删除初始化标记触发不可控全量重建。

旧 `credit::history_session` 还用于 history 引用长度校验；存储容量与单引用/读取协议上限必须拆开定义。提高历史额度不能造成 A 接受而 C/CW 拒绝描述符，也不能无意扩大单帧或内存分配上限。

## 7. 容量满时的正确行为

当前 `Store::fail` 在识别容量触发器后仍调用 storage-failure callback；Agent 因而停止。现有 `native/tests/history_budget.cpp` 明确断言此行为，修改时必须重写预期，不能只删回调让任务继续无保障执行。

先区分：安全准入拒绝、已执行后的容量违约、真正 I/O/完整性失败。

- **副作用前：** 在同一可靠请求准入事务内预留操作所需最小持久空间，包括开始/完成/失败记录；不足则持久返回明确背压，不能先启动 thread/turn 再发现无法写入。同 requestId 查询应得到一致结果，不暗中重新执行。
- **运行中：** 已发布信用和已开始任务的终态/必要输出必须有对应预算。未知总输出使用有界窗口、持久输出缓冲和上游可验证的暂停机制；不能靠一个小预留承诺无限生成。若 Codex 无法安全暂停/限流，在无法保证继续记录时仍须停止相关副作用、保留未知证据，不能仅吞掉写失败。
- **控制路径：** 读取、查询原结果、权限撤销、精确停止、必要 ACK 和诊断保有独立容量与调度机会。仅缓存满不应关闭整个 Agent；真正磁盘故障仍按安全停写流程。
- **创建关联：** 保留 `operation_session` 的请求/session 原子关联；无法确认外部初始化终态时仍返回未知。调查本机原创建结果时按原 requestId 和会话证据核对，不能用新请求试探。跨 SQLite/Codex 的副作用不声称 exactly-once。

预算原理保持：`已用 + 未兑现预留 <= 配额`。释放预留只在安全确认、未执行取消或明确退休完成后；重启必须重建预留，不能仅计算剩余正文大小。旧库已超限是受限迁移状态，不是允许继续超额承诺。

## 8. 迁移、归档与失败恢复

1. 先做只读审计，输出按表、会话、来源、固定原因及预算组成的汇总；不要在报告打印正文或凭据。使用已有 SQLite 在线备份工具保存含 WAL 一致性的检查点，保存配置和程序身份。
2. P1 只迁移策略和准入，不删除历史；已有超限进入可诊断的受限状态，用户可显式调大合理额度后重启。
3. 正文合并在单事务内生成新块、核验摘要、改引用、删旧块及同步计量；崩溃恢复必须只看到旧完整版本或新完整版本。迁移临时空间单独有上限，不能为去重先复制整库。
4. 为每类历史建立 Codex 回源映射；只有只读重取、标准化摘要、权限和重启恢复通过，才标记可淘汰。不能匹配的旧记录保留，不根据“看起来像聊天”批量删除。
5. 回源不可用、原文清理、旧修订不存在时保留必要本地快照；如果操作者要主动减少唯一历史副本，另做显式可审查的归档/删除方案和引用影响报告，不作为自动缓存清理。
6. SQLite 删除行一般只增加空闲页，文件不一定缩小；WAL checkpoint/incremental vacuum 另行在低负载、足够余量下处理。验收分别记录账面、逻辑正文、DB/WAL/临时峰值，不能混用。
7. 禁止自动回退旧程序读取新库；需要恢复时停止实例并核对备份之后的请求及真实副作用，恢复配套程序/配置/数据库。不得把旧快照里的待办当成新意图重放。

### P2 小 delta 尾块合并（实施中）

`Store::project` 追加流式正文时复用最后一个 chunk：只有旧尾块与新 delta 的 UTF-8 字节合计不超过 4096 时才原位追加，否则新建块。单个较大 delta 沿用已有受限输入路径，不复制成多个小块。公开 start/offset 仍是 SQLite Unicode 字符位置，不能按字节推进。

复用现有 chunks 主键、bodies 长度和记账触发器，不增加持久字段。读者仍为 `content` 与 history reference；写入、正文长度、revision 和记账沿用 `event_batch` 原事务。投影后续写入失败会同时回滚尾块追加与预算变动。封存正文不因合并丢失，原始 events、公开序号和引用保留语义不变。

专项使用 3000 次 `你🙂` delta：新布局为 6 条 chunk（逐 delta 布局原本为 3000 条），核验 4096 字节尾块上限、跨块/跨页随机字符 offset、重启重读和故障回滚。这是该样本的 chunk 记录收益，不代表整库磁盘缩减；原始事件仍逐条保存。旧块的有界事务合并见下一节；其它正文去重仍待实施。


### P2 旧分块后台合并（实施中）

`Store::cleanup` 沿用 Agent 现有 30 秒维护周期，每轮调用一次有界合并（副本测试连续调用，不代表线上完成耗时）：按 `(seq,start)` 最多检查 128 条 chunk，每条只读取不超过 4096 字节的候选正文，总候选正文不超过 512 KiB。仅合并同一 seq、字符偏移连续且合计不超过 4096 字节的相邻块；大块、偏移缺口和仍有持久历史预留的会话跳过。不会改写 events、history、bodies 或公开 revision/seq。

扫描位置是 Store 内存中的调度提示，不是必要持久状态；重启可重扫且幂等。合并在独立 SQLite 写事务内先删除被吸收块、再更新前块并逐字节核验结果，现有记账触发器同步退款。任何一步失败回滚整个批次，正文读取只能看到提交前或提交后的完整布局；不引入新表、双份正文库或新的协议字段。

对已超限旧库也允许净减占用的合并。首次实际合并前，在持有 `BEGIN IMMEDIATE` 写锁的事务中保存并临时移除容量增长触发器；其它记账及预留触发器继续工作。提交前核验全局和每个会话的字节/记录均未增加，恢复原容量触发器后才能提交。其它连接无法在这一窗口写入；DDL 与数据同事务，失败或进程退出回滚会恢复触发器和旧正文。无候选时不变更触发器。不放宽 JSON 配额、不新增持久维护标志，不为合并先复制整库。

专项构造 1000 条旧 Unicode chunk：分批跨重启后剩 2 条，原引用摘要、正文长度、历史快照及公开游标不变；验证活动预留不消耗、删除后更新故障完整回滚、重复维护不二次退款，以及调低到现有占用以下仍能净减合并、合并后容量限制继续生效。正式本机数据库未运行该迁移。


本机旧库隔离副本验证：40,163 条 chunk 经 314 个批次合并为 363 条，计费占用从 288,563,401 字节降至 185,445,423 字节（275.20 → 176.85 MiB），最大单会话从 67.54 → 40.36 MiB。355 份按字符偏移重建的正文 SHA-256 不变，events/history/bodies/streams/external_items 的排序行摘要不变，SQLite 完整性检查通过。此处只证明副本在本次数据集上的计费/记录收益，不代表物理文件缩小、所有旧库都能回到额度内或完整优化方案已完成。脱敏汇总见 [packing.json](assets/history-storage-2026-11-02/packing.json)，原始私有证据位于 `.local/history-implementation/packing-verification.json`。


### P3 只读精确条目读取与来源校验（实施中）

C++ `read_history_thread` 统一校验 thread ID、项目 canonical cwd 与历史模式；普通会话、外部会话的归档加载均经此入口，未知模式明确拒绝。`read_history_item` 只使用 `thread/read` → `thread/items/read` → `thread/read`，每次仅请求一个明确 turn/item；拒绝缺失、重复、错 turn/错 item、无效结构和超过调用预算的条目，读取后再次检查项目与模式。禁止借此调用 resume/start/turn 或自动回退业务执行。

单次返回条目的序列化 JSON 最多 1 MiB；上游解析仍受 CodexProcess 既有有界缓冲保护。该入口暂不提供大条目回源分页或 legacy 分页查找，能力不足/错误保持明确失败。它返回**当前持久条目**，不是旧 history revision 的恢复证明；还没有替换 `Store::content` 的本地正文读取。未增加来源持久表，未启用自动淘汰，`readPageMaxBytes`/`readConcurrency` 配置尚未开放。

专项 `native-history-source` 使用只允许初始化与读取 RPC 的确定性 peer，覆盖 18 个成功/失败场景，包括项目重绑、历史模式改变、未知模式、缺失、重复、身份冲突、大小边界和不支持的 API；错误不触发无限扫描或执行型降级。

真实只读调查使用本机 Codex 0.166.0：userMessage、agentMessage、commandExecution、reasoning、webSearch、mcpToolCall、fileChange、contextCompaction、imageView、sleep 各一个已完成样本，每个在两个独立 app-server 进程通过该 C++ 入口重读，完整条目序列化摘要一致。没有模型调用，运行时入口不直接读取私有数据库。调查工具仅以只读数据库选择样本身份，正文由 API 读取；脱敏证据见 [source-read.json](assets/history-storage-2026-11-02/source-read.json)。

剩余前置条件：来源用户环境/实例持久绑定、版本化脱敏投影与原 history 摘要比对、legacy 有界查找、旧修订/来源删除/替换、读取并发与缓存策略。当前样本没有 plan；未证明 0.164.0、所有活跃 writer 或同类型全部变体可回源，因此不能将整个类型直接标记可淘汰。


### P3 版本化投影与差异接受规则（实施中）

`history_projection.cpp` 提取现有 external 快照的脱敏、正文选择和去重指纹，Store 写入与重建共用 `project_history_item` v1，保持旧存储字节语义。普通事件使用独立的 `event-v1` 投影：助手 delta 取 text、命令输出取 aggregatedOutput，其它支持的 item 事件保留原事件 envelope，并按原字段形态处理新增生产时间字段。

`recover_history_content` 始终验证原引用长度和 SHA-256；允许已验证前缀或登记的命令输出片段恢复，拒绝越界/错位以及实质改写。开始态和完成态不因“可接受最新值”而混用原 revision。此接口尚未接入 `Store::content` 的缓存缺失回源，来源身份/偏移持久化及最新视图更新仍待实施；没有自动删除正文。

本机隔离旧库与真实 Codex 的逐条比较范围为 4316 条可关联历史，另 443 条所属项目不在当前配置中，不跨项目探查。初始投影仅 1289 条摘要完全匹配；去掉新增生产时间字段后增至 3337 条，另有 2 条原文前缀、28 条命令输出片段可重建。28 条片段均经 C++ 恢复接口验证原摘要通过。最终可精确恢复 3367 条；剩余 945 条实质差异中，941 条是开始态，4 条终态源输出已截短，另有 4 条源条目缺失（其中终态 1 条）。除开始态外，2774 条候选中 2769 条可精确恢复（约 99.82%）。[脱敏比较结果](assets/history-storage-2026-11-02/recovery-comparison.json) 记录完整分组与边界。这是已关联样本的恢复覆盖，不是全库可淘汰率；不因少数必要快照禁用其余条目回源，也不能把源条目截短误报为旧正文可恢复。
