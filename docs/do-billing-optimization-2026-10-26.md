# Durable Objects 计费优化方案

日期：2026-10-26。状态：**0.5.12 已实现并通过本地回归；部署与测试身份见 TEST_REPORT，未验证线上节省**。

本文依据当前代码和用户提供的 [Durable Objects 文档索引](https://cloudflaredoc.ubitools.com/durable-objects/llms.txt)，并用 Cloudflare 官方文档核对计费和 API 语义。下文保留设计依据及旧代码基线，实施差异见第 8 节；价格与额度是查阅日快照，实际以账户账单为准。

## 1. 结论与范围

保留 Worker + 单个 RegistryDO + 每主机一个 HostRelayDO，以及现有 SQLite 后端。本文中“A–Worker”“C–Worker”包含 Worker 路由后的 HostRelayDO / RegistryDO；实际长连接由 DO 使用 Hibernation API 接受，不让入口 Worker 长期运行转发循环。

**按最新决定，以客户端需求驱动通讯：A 空闲时不保活、不做超时探测、不周期复核；CW 使用事件通知和刷新按钮；CC 在运行期间按 10 秒刷新。** 此决定替代上一版“5 分钟空闲复核 + 自动响应心跳”的设计。

| 场景        | 目标行为                                                       | 稳定、无业务变化时的周期用量                      |
| ----------- | -------------------------------------------------------------- | ------------------------------------------------- |
| 只有 A 在线 | 注册及协议协商后等待实际消息；无心跳、授权复核、审批或更新轮询 | 应用主动周期请求、周期 alarm 和周期存储写入均为 0 |
| A–CW 已连接 | 首次快照、事件推送、用户手动刷新；不设置状态轮询或保活         | 无多余周期通讯；真实事件、用户操作和恢复有用量    |
| A–CC 已连接 | 实时业务仍走 WS；一个共享调度器每 10 秒刷新一次所需状态        | 每个运行中的 CC 最多每 10 秒一轮查询；结束后停止  |

CW 的“刷新”按钮读取当前视图的权威快照，并在需要确认 A 可用时发起按需探测。CC 的刷新是明确允许的轮询，不再要求全部 C 客户端零轮询；一次性命令只读取所需状态后退出，不启动脱离命令生命周期的后台刷新服务。

授权在连接建立、真实请求及事件转发前验证，保留原最长 5 秒的按需缓存和主动撤销通知；缓存过期只在下次使用时重新检查，不启动刷新定时器。主动撤销通知丢失时，空闲连接可以保留到下次活动，不再承诺固定时间内关闭；后续数据仍必须通过授权校验。

“基本不产生用量”指稳定空闲连接没有应用主动产生的周期流量，并非套餐费、已有存储、握手、断线重连、真实通知和有限到期清理全部免费。无人查看时仍有任务输出或新审批申请，属于实际业务事件，不能计作空闲。

本次按用户指令实现、测试、提交并部署；不调用真实模型。旧代码基线保留在第 3、4 节，不能把目标写成当前行为。既有性能优化见 [性能修复记录](perf-fixes-2026-10-25.md)。

## 2. 正确的计费口径

### 2.1 请求、时长与存储分别计算

当前 `wrangler.jsonc` 以 `new_sqlite_classes` 创建两个 DO 类。因此即使代码调用 `storage.get/put/list/delete`，也应使用 SQLite 行读写口径，不能套用旧 KV 后端按 4 KiB 的计费方式。

| Paid 维度   |  包含量 / 月 |           超出单价 |
| ----------- | -----------: | -----------------: |
| DO 请求     |       100 万 |       $0.15 / 百万 |
| DO duration | 400,000 GB-s | $12.50 / 百万 GB-s |
| SQLite 行读 |       250 亿 |    $0.001 / 百万行 |
| SQLite 行写 |     5,000 万 |     $1.00 / 百万行 |
| SQLite 存储 |   5 GB-month |   $0.20 / GB-month |

请求计量包括 HTTP、DO stub RPC 和 alarm；入站 WebSocket 数据消息按 20:1 折算，出站消息及协议层 ping 不收请求费。SQLite 删除计入行写，每次 `setAlarm()` 也计一行写。额度在账户相应维度汇总；Paid 超额用量按计费单位向上取整。Free 超限会拒绝相应操作，不按 Paid 超额价格继续服务。以上依据 [官方定价](https://developers.cloudflare.com/durable-objects/platform/pricing/)。

### 2.2 不把连接时间或唤醒次数直接当作 duration

DO 使用 Hibernation API，空闲且满足休眠条件时就不再计 duration，**不需要等运行时实际移出内存**。生命周期文档中的约 10 秒是运行时状态转换说明，不能按“唤醒次数 × 10 秒”估算收费。待完成的网络 I/O、事件、`waitUntil` 和 `setTimeout/setInterval` 等会影响休眠资格；一个 DO 同时处理多条请求时，按实际重叠时间计算，而不是逐请求耗时相加。[生命周期](https://developers.cloudflare.com/durable-objects/concepts/durable-object-lifecycle/)、[计费 FAQ](https://developers.cloudflare.com/durable-objects/platform/pricing/#when-does-a-durable-object-incur-duration-charges)

`acceptWebSocket()` 允许连接跨休眠存活，但内存会重建，必须从持久状态和 WebSocket attachment 恢复必要上下文。已有连接不等于持续计时；待处理控制请求则不能被当成“空闲”。[WebSocket 休眠](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)

## 3. 当前代码中的成本来源

代码入口使用相对路径和函数名，行号变化不影响定位。

| 来源                                                  | 已确认行为                                                                                                | 成本与优化边界                                                                                                                    |
| ----------------------------------------------------- | --------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| [HostRelayDO](../apps/relay/src/host.ts) `upgrade()`  | `acceptWebSocket()` + attachment，最多 40 个连接                                                          | 已支持休眠；不需要更换连接架构                                                                                                    |
| `authorized()` / `forward()`                          | 最长 5 秒内存缓存，同 hash 在途合并，最多 128 个缓存项；接收者独立队列                                    | 休眠会丢缓存；持续流量并非每帧都跨 DO 鉴权                                                                                        |
| `alarm()` / `schedule()`                              | 有连接时执行结束后约 30 秒再检查；新连接/票据可提前到 5 秒；唯一 hash 分组、最多四路鉴权；扫描全部 ticket | alarm 请求、重新设 alarm 的行写、Registry 子请求和扫描；短缓存不保证跨 alarm 命中                                                 |
| [Agent](../native/src/agent.cpp) `heartbeat()`        | 每 30 秒发 JSON ping；超过 90 秒未收 pong 时关闭连接                                                      | 普通数据消息进入 DO handler，先鉴权，再读 `agentEpoch`，最后回复 pong                                                             |
| Agent `check_client_requests()`                       | 启动及约 30 秒维护周期查询 `/api/v1/agent/requests`                                                       | [Worker](../apps/relay/src/index.ts) 先 `auth` 再 `agentDevices`，每轮两次 Registry 请求；后者在事务内复核 Agent 并扫描待审批记录 |
| [网页](../apps/web/src/main.tsx) `refresh()`          | 每 15 秒查询 `/hosts` 和 `/auth/me`，不依赖页面可见性                                                     | `/hosts` 对每个有效主机凭证执行 Registry auth、host 读取和 HostRelay status；多标签页重复                                         |
| 网页管理员刷新 effect                                 | 只以 `admin` 为条件，每 3 秒读 devices、api-keys、hosts                                                   | 即使切到 CW 仍运行；每个接口通常各有鉴权和数据查询两次 Registry 请求                                                              |
| 网页离线唤醒 effect                                   | 选中离线且可唤醒主机时每 3 秒读 `/hosts`，每分钟请求唤醒                                                  | 与全局刷新重叠，且轮询全部授权主机；HostRelay 外部唤醒 GET 最长等待 10 秒                                                         |
| [RegistryDO](../apps/relay/src/registry.ts) `alarm()` | 有临时记录或未过期 owner 时约每分钟扫描 device、limit、auth；永久设备凭证本身不续 alarm                   | 重复扫描长期凭证；owner 8 小时有效期内可带来持续清理轮次                                                                          |
| HostRelay `command()`                                 | 最多 64 个在途控制请求，每个有 12 秒超时                                                                  | 等待 Agent 时仍可能产生 duration；超时具有结果不确定语义，不能为了省钱提前宣称失败                                                |

当前最多五个有效主机，Registry 不是每主机一个。不能把“每个主机都有一个全天常驻 Registry”计入估算，也不以大规模分片替代小规模调用收敛。

## 4. 可复算的基线

### 4.1 单 Agent 在线、无网页、无任务

假设 30 天、连接稳定、无网络错误或重试、无额外管理操作。周期次数忽略 handler 耗时和初始 schedule，仅用于容量规划。

| 路径                          |              每天 |                                              30 天 |
| ----------------------------- | ----------------: | -------------------------------------------------: |
| Agent JSON 心跳数据消息       |          2,880 条 |                   86,400 条，折算 4,320 个 DO 请求 |
| HostRelay 周期 alarm          |       约 2,880 次 |             约 86,400 个请求及同量 `setAlarm` 行写 |
| Agent 待审批 HTTP 查询        |       约 2,880 次 | 约 86,400 次 Worker 请求、172,800 次 Registry 请求 |
| 心跳 + alarm 的 Registry 鉴权 | 约 2,880–5,760 次 |                 约 86,400–172,800 次 Registry 请求 |

最后一行的区间反映 5 秒缓存、在途合并与两种事件的相位；休眠重建或超过缓存窗口时无法复用，不是平台保证的上下界。综合约 **349,920–436,320 个 DO 请求 / 主机 / 30 天**，不含连接建立、Registry 自身清理、额外凭证和重试。五主机约 175 万–218 万，尚未加入网页流量。SQLite 行读需按实际操作另计，不能把一个鉴权请求当成固定一行读取。

上述为当前实现基线。新方案取消应用心跳、周期授权复核和 Agent 后台状态查询；新目标按 A、CW、CC 分别估算，见 4.4，不混入这张基线表。

### 4.2 管理页面和主机列表

管理员三个接口每 3 秒轮询一次，每次各两次 Registry 调用，理论值为 `3 × 2 × 86,400 / 3 = 172,800` 次 Registry 请求 / 日；持续 30 天约 **518.4 万**。这不含全局刷新。实际受登录有效期、浏览器后台计时器节流和打开时长影响，不能视作普通用户每月必然产生的用量。

一个拥有 `H` 个有效主机凭证的网页，每 15 秒调用 `/hosts`，仅该接口就是约 `5,760 × 3H = 17,280H` 次 DO 请求 / 日。管理员数据按当前 Tab 加载、后台停止刷新、同标签页合并相同查询，优先级高于微调单条心跳。

### 4.3 费用模型

定义 `F` 为所有进入 DO 的 HTTP/stub 调用数（包括 Worker→DO、DO→DO 和 WS 握手），`A` 为 alarm 次数，`M` 为入站 WS 数据消息数：

```text
R = F + A + M / 20
D = 0.128 × Σ每个 DO 的计费活跃秒数
请求超额费用 = ceil(max(R - 1,000,000, 0) / 1,000,000) × $0.15
时长超额费用 = ceil(max(D - 400,000, 0) / 1,000,000) × $12.50
```

这是按官方示例内存换算与计费取整建立的 Paid 模型，账户其他应用用量需先合并。存储、Workers 套餐/请求/CPU、日志等另算。`D` 应从受控环境计量，不能由连接时间或查询间隔倒推。新方案不发送应用心跳，因而不依赖心跳自动响应是否计请求费的假设。

### 4.4 新目标下三类场景的用量

假设连接稳定、初始同步已完成，没有业务变化、尚未结束的请求、待清理记录、故障恢复或用户操作：

| 场景                           | 每天应用周期查询 / 消息 |           30 天 |
| ------------------------------ | ----------------------: | --------------: |
| 只有 A 在线                    |                       0 |               0 |
| A–CW 连接，用户不刷新          |                       0 |               0 |
| 一个 CC 全天运行，每 10 秒刷新 |           最多 8,640 轮 | 最多 259,200 轮 |

这里的 CC“轮”是客户端逻辑查询，不是一个计费 DO 请求。一次 HTTP 刷新可能调用 Registry、HostRelay，并产生 A 的响应帧、状态通知及 ACK；设平均每轮 DO HTTP/stub 调用为 `k`、入站 WS 数据消息为 `m`，则该路径 30 天请求用量约为 `259,200 × (k + m / 20)`，另加握手、其他业务、alarm 和重试。多个 CC 实例分别累加；命令只运行一小时则最多 360 轮，不按全天估算。

同一 CC 内合并主机状态、待处理结果等需求，不为每个界面或请求各起一个 10 秒定时器；本轮未完成时跳过下一拍，不堆积查询。可一次返回聚合状态，但不能把跨 DO 调用或 A 响应的用量省略。

上述 A/CW 的零周期用量依赖取消所有隐藏探测路径，并且 DO 满足休眠条件。平台实际断开、网络设备回收空闲连接和重连会产生额外活动；无保活策略接受这种可能性，不以固定探测换取在线状态实时保证。最终仍需受控环境测量。

## 5. 优化设计

### P0：计量与调用归因

区分 Worker→Registry/Host、Host→Registry、A 入站业务帧、CW 操作与通知 ACK、CC 刷新、连接建立/关闭、到期清理和恢复请求。记录缓存命中、合并请求、事件量及处理耗时，不逐消息写存储来计数，也不记录凭据、正文或唤醒 URL。现有 10% 日志采样不能未经校正视为完整计数；以平台请求、duration、SQLite 行读写和存储量核对。[官方指标说明](https://developers.cloudflare.com/durable-objects/observability/metrics-and-analytics/)

验收必须分别报告“只有 A”“A–CW”“A–CC”，不能把 CC 的允许轮询混入 CW，也不能把有任务输出的 A 当成空闲。

### P1：A–Worker 空闲不产生主动通讯

1. 取消 Agent 每 30 秒 JSON ping、90 秒无 pong 断开及其定时器，不改成另一种周期协议 ping 或自动响应心跳。检查 [原生 WS transport](../native/src/socket_impl.hpp) 的运行库空闲超时和自动 ping 配置，防止应用层取消后底层仍周期探测或主动断开。
2. 取消 HostRelay 和 Registry 对长期已认证连接的周期授权复核，包括前一版 5 分钟计划。不因 `getWebSockets()` 非空就续 alarm，不在构造器安排周期检查。
3. Agent 待审批、版本检查改为真实变更通知。首次注册、协议协商、已知断线后的重连可以同步一次；稳定空闲时不查询“是否有变化”。本地进程回收、文件维护等不产生云端请求的工作不属于本次删除范围。
4. 接受静默断链延后发现。明确的 socket close/error、网络恢复或实际发送失败可以触发连接恢复；不因“多久没消息”探测或重连。已知失败后的连接尝试采用有限自动重试与退避，超过预算等待网络恢复或显式重新连接，不形成无人使用时无限重试流量。
5. 不对稳定的 A–Worker 链路设置应用存活超时；既有 DNS、建连、TLS/代理握手的有限操作期限不用于周期检查。TLS 校验、协议协商、容量与消息大小限制继续有效。

只有空闲连接时 DO 应可休眠。若此时仍存在 pending Promise、`waitUntil`、定时器或出站 I/O，必须找出实际原因，不能仅因关闭了 heartbeat 就宣布完成。

### P2：C 按需确认 A，Worker 不长期等待

当前 HostRelay `/status` 仅依据登记的 socket 和 capabilities 返回在线，**不足以在查询时发现静默断链**。目标应区分“连接已登记”和“本次查询得到 A 响应”，不能把旧状态当作实时可达。

流程如下：

1. C 首次需要 A、CW 点击刷新、CC 到达 10 秒刷新时，发送带 requestId 的状态查询或真实业务请求。查询自身不产生副作用。
2. Worker/HostRelay 验证 C、目标主机及 A 身份；已知离线立即返回状态。若仍有登记连接，按需发送一次探测，或直接以该次真实业务响应确认可用，不额外叠加探测。
3. HostRelay 登记有界的关联信息、发送请求后立即返回“已受理/等待回应”，结束事件处理。A 返回后再通过 C 订阅发送关联结果；不在 DO 内持有等待 A 的 Promise、12 秒计时器或长期 HTTP 响应。
4. 等待期限由 C 管理，只影响本次查询的展示或命令返回，不构成 A 链路的存活超时。未收到响应时显示“未确认/请求结果未知”，不把它误判为远端操作必然失败，不自动重做有副作用的命令。
5. 明确断线、实际传输失败或后续 C 重试时执行必要恢复；若两端都未察觉静默断链，本轮 C 查询可能只能得到超时/未确认，不能承诺查询一定能自动修复网络。A 后续重连后通过快照恢复状态。

现有 `command()` 的“在 DO 中等待 12 秒”必须改成可恢复的关联结果协议，**不能只删除超时而留下永不结束的 Promise**。浏览器和 CLI 依靠 requestId 接收结果、主动取消本地等待或下次刷新查询结果；客户端离开后不持续轮询。

查询关联信息不以无限内存队列保存：每个 C 最多一个状态探测，重试复用或替换该只读查询的代次；连接关闭、结果返回或用户取消时释放，无响应时受既有主机容量约束，达到上限拒绝新请求。业务完成状态、审批和去重信息仍保留在权威持久存储中，不以丢弃请求身份解决容量问题。迟到结果需按 requestId/epoch 处理，不能投递给后来占用相同位置的请求。

### P3：CW 事件通知与刷新按钮

CW 页面和管理页面取消固定间隔状态查询，也不发送应用保活。首次进入视图取快照，此后实际变化通过事件更新。对主机、审批、设备、API Key、唤醒配置、创建结果等使用 scope + revision 识别变化，必要时只读取受影响数据。

**刷新按钮是必需的用户流程**：

- 位于主机/会话状态区及管理数据视图，刷新当前视图，不清空草稿、历史、审批或重发创建任务。
- 点击后立即显示加载状态，合并重复点击；需要 A 的数据执行 P2 按需确认。成功后展示最新状态或最近确认时间。
- C 侧等待结束后显示未确认/失败和可重试状态，不保持无限旋转，不在后台自动继续刷新；未结束的远端操作仍以原 requestId 恢复。
- 已知断线时可在用户刷新时重新连接，完成快照同步后继续事件订阅。后台隐藏再恢复可见是一次恢复事件，可重新同步，但不启动定时查询。

首次订阅与快照应具备版本边界：先建立订阅并缓冲变化，再交付对应版本快照，随后按序应用事件。跨 DO 状态不声称具有全局原子快照；主机数据分别带版本，断口或过期游标触发一次快照恢复。

没有会话或 A 离线时，CW 仍能订阅主机状态；该订阅不要求 A 在线、不获得会话控制权，不能直接复用当前要求 A 在线的业务 WS 升级入口。Registry 接受管理员及待配对申请的入站 Hibernation WS，HostRelay 接受按主机隔离的订阅，优先复用已有通道，不持有 DO 出站长连接。

### P4：CC 每 10 秒统一刷新

CC 保留实时业务 WS 收发，并允许运行中的交互/等待流程每 **10 秒**查询所需状态，作为它的刷新和静默断链发现机制。第一次立即查询，后续最多每 10 秒一轮；上一轮仍在等待时不叠加新轮次。退出命令、结束交互、授权失败或等待流程结束后立即停止。

同一实例的主机状态、待审批登录结果及未完成操作查询合并调度；能由返回事件提前完成等待时立即完成，不必等到下一拍。一次性 `hosts` 等命令取一次快照就退出；正在等待唤醒的 CC 使用同一 10 秒节奏，保留其明确的总等待期限，而不是另外运行原 2 秒轮询。10 秒是刷新节奏，不是 A 的断线超时或所有任务的执行期限。

CC 只查询命令所需目标，不每轮遍历全部主机、凭证和历史。优先提供“验证身份并返回所需元数据”的聚合查询，减少 Worker 对 Registry 的重复调用；多客户端同时查询同一 A 时可合并在途只读探测，但结果必须按各自授权 scope 返回。

### P5：授权按活动检查，不周期检查连接

主动撤销继续写权威状态并尝试立即关闭相关连接。撤销通知丢失时允许空闲连接仍登记着，不再保证 30 秒或 5 分钟内断开；连接存在不等于授权有效。

在 C 查询、业务发送、A 入站帧以及向 C 转发事件前，验证对应凭证、角色、hostId、API Key、主机禁用状态和到期时间。向 A 下发命令前也检查 A 的身份，不能只验证发起命令的 C。仅在实际使用时复用原最长 5 秒鉴权缓存，并保留同 hash 在途合并；DO 重建后无缓存就重新查询。不得让无业务流量的身份检查自行安排 timer/alarm。

撤销与在途鉴权竞争仍需要版本/token 防护，旧响应不能重新填回已撤销权限。Registry 不可用时拒绝放行。通知订阅、管理员和配对申请仍分别授权；公开 ID/配对码不足以订阅申请状态，网页继续使用 HttpOnly Cookie 和 Origin 检查，不把秘密放入 URL 或通知。

owner、配对申请、票据及未认证握手的有效期仍须执行；它们是有限授权/请求的期限，不是 A 的存活探测。安全敏感的到期状态变更需要时安排一次性 alarm，其他记录可在访问时检查并合并清理，不恢复按分钟扫描全库。

### P6：通知、结果与后台操作的恢复

| 现有行为                                 | 目标行为                                                                                                     |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 网页 15 秒主机/身份、管理员 3 秒列表刷新 | 首次快照、变更事件、刷新按钮及重连同步                                                                       |
| Agent 30 秒待审批查询                    | 指定主机的新申请或状态变化时通知，启动/重连同步一次                                                          |
| CW 3 秒、CC 2 秒等待上线                 | CW 事件通知和手动刷新；CC 共用 10 秒刷新                                                                     |
| CW 每分钟重发唤醒                        | 用户操作触发一次，保留服务端 60 秒去重；等待状态变化，需再次唤醒时由用户显式重试                             |
| CW/原生每 2 秒 devicePoll                | CW 订阅自身申请，事件到达后领取；CC 等待登录时按统一 10 秒刷新，可被事件提前完成；A 初次配对采用申请事件通知 |
| CW 5 秒创建结果查询                      | A 提交结果后发送完成通知，按原 requestId 取权威结果；手动刷新和重连恢复                                      |
| Agent 定时下载更新清单                   | 发布变更通知后读取清单，启动/重连/显式 update 同步一次；不再周期查询                                         |

通知承载最小状态/版本，不传原始凭证。领取继续保留原轮询秘密、CW 单次原子交付、原生原期限内可重取与 hostId 核对，批准后被撤销则不可领取。版本发布入口须有鉴权与幂等，产物就绪后才发布；版本通知不替代下载来源、完整性及协议校验。`autoUpdate.intervalHours` 的废弃和旧配置兼容留到实现时明确，禁用更新及空闲安装约束保留。

通知以权威状态为准，采用可重复的 revision/eventId 与有界记录。状态提交后尝试推送；ACK 仅确认已处理或持久化的版本。**A–Worker 不设置 ACK 超时重传、周期待发扫描或周期版本对账**，不能把心跳改名为可靠投递又引入持续流量。未送达事件由下一次真实活动、明确重连、CW 刷新或 CC 10 秒查询补快照/结果；客户端不在线时不反复向其投递。

这接受无人查询且连接静默失效时通知延迟，甚至直到下一次恢复才发现新状态。在线但漏事件时不承诺有界时间内自动修复；CW 刷新按钮是恢复入口，CC 的 10 秒查询提供其补偿。需要投递的数据保存在权威结果/状态中，不能只存在内存队列；有限事件日志超限后允许回退快照，业务去重身份和完整历史不可随之删除。

Registry→HostRelay 的通知使用短调用；失败可记录变更版本供下次同步，不使用持续重试 alarm 维持“实时在线”承诺。DO 重建、Agent 重启和客户端重连时按版本恢复；关联结果的 epoch、接管、流控和 40 连接预算仍适用。慢消费者达到有界预算后关闭并通过快照恢复，不无限缓冲。

### P7：仅保留有限到期工作

Registry 按 device、limit、owner 等真实到期点清理临时状态，永久设备授权不进入到期队列。HostRelay 按票据和握手 deadline 处理有限工作；没有这些任务时，即使 A/CW socket 仍存在也不设置 alarm。无连接但有未到期票据仍须可回收，避免目前提前检查后因无连接而不续调度导致残留。

一个 DO 只有一个 alarm，且 handler 可能重复执行，需合并到最早到期点、幂等处理。不要构造时无条件设置 alarm，也不要把处理结束后固定延后若干秒当作新周期。[Alarms API](https://developers.cloudflare.com/durable-objects/api/alarms/)

到期索引使用有界迁移，计入新增行写与索引维护成本；业务读取独立检查有效期，不能依赖准时物理删除。[SQLite API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)

不删除 agentEpoch、有效 lease、权威结果或去重身份来压缩库，也不在客户端断开时直接 `deleteAll()`。这些属于正确性状态，和取消链路空闲探测是不同事项。

## 6. 验收与实测

以下为完整验收矩阵，实际已执行范围与未验证项以 TEST_REPORT 为准。

| -------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 只有 A、无任务 24 小时     | 初始握手和有限清理结束后，无应用 ping、周期鉴权、审批/更新查询、ACK 重传或维护 alarm；底层未隐式发保活              |
| A–CW、无操作无变化 24 小时 | 无额外周期状态请求或周期 alarm；有实际事件才发送通知和必要 ACK；满足休眠条件，未挂起等待 A 的处理器                 |
| CW 刷新                    | 按钮可见，单次读取/按需探测，重复点击合并；有加载、成功/最近确认、失败/未确认状态，不清草稿、不重复执行命令         |
| A–CC                       | 首次立即查询，后续最多每 10 秒一轮，上一轮未完不叠加；只查所需数据，命令结束停止，事件可提前完成等待                |
| 静默断链                   | 无 C 时不主动探测；CW 刷新或 CC 查询触发实际 A 往返，未回应显示未确认，不把登记 socket 当作本次可达证据             |

| 控制结果                   | DO 转发后及时结束 handler，没有永不结束的 Promise；C 超时不等于远端失败，迟到结果、重启恢复和重试保持幂等           |
| 休眠及流控恢复             | attachment 恢复，epoch/lease 不倒退，pending 和 receipt 预算不可因重建绕过，不丢审批及权威结果                      |
| 通知漏失与恢复             | 覆盖提交后崩溃、快照竞态、乱序、重复、漏通知、ACK 丢失、游标过期；通过实际活动/刷新/重连恢复，无周期重试 A          |
| 到期清理                   | 无连接票据可清；临时申请到期正确撤销未领取结果，不误清永久授权；任务清空后 alarm 停止                               |

测试矩阵覆盖 1/5 个 A、CW 可见/隐藏、CC 一次性命令与长时间交互、多客户端同时刷新、四会话真实任务、慢 Registry、慢读者、静默断链和离线唤醒。分别记录请求、duration、行读写、存储、结果延迟、重连及错误，而非只数定时器。

DO 实际休眠、平台连接回收和费用需在独立 Cloudflare 测试 namespace 验证。本地 Wrangler/Vitest 只能证明逻辑。不能承诺“任何网络下零额外用量”，也不能把 C 查询时才发现失联算作原实时在线保证未退化；这是明确接受的新行为。

## 7. 后续交付与回滚

建议顺序：建立三场景基线 → 可恢复的异步请求结果及事件通道 → CW 刷新和 CC 10 秒调度 → 按需鉴权与故障恢复 → 取消 A 心跳/超时探测/周期复核及后台轮询 → 验证无隐藏周期活动。不能先删 DO 控制超时而保留等待 Promise，也不能在事件和快照恢复可用前删除唯一状态来源。

新协议需协商。旧 Agent/客户端在过渡期可保留原心跳和查询，但不得计入新目标验收；新客户端遇到旧 Relay 应提示升级或明确显示兼容模式，不能静默声称零周期用量。回滚保留可读的授权、票据、lease、请求身份和结果，恢复旧版本后如实标注周期流量恢复。

实现时同步更新 [架构](ARCHITECTURE.md)、[需求](REQUIREMENTS.md)、[用户指南](USER_GUIDE.md)、[开发指南](DEVELOPMENT.md)、[测试记录](TEST_REPORT.md)、[发布说明](RELEASE.md) 受影响部分及 `CHANGELOG.md`，尤其注明 CW 刷新按钮、CC 10 秒刷新、A 无存活探测和静默断链后的未确认状态。本次实施使用既有账号及 DO 绑定，不轮换生产 secrets。

## 8. 0.5.12 实施说明

已接入持久异步控制、独立 Host / Registry 入站休眠通知、CW 刷新、CC 十秒调度、Agent 按需审批 / 更新与有限重连，以及到期索引迁移。详细协议、兼容限制与临时五分钟传输回执说明见 USER_GUIDE 和 ARCHITECTURE。新客户端使用 X-CoC-Async:1；旧 Agent 可以兼容原 protocol 1，但仍产生原周期流量，新 probe 需要升级。

通知采用持久 revision 加权威快照失效信号，不维护正文增量事件日志；先订阅再读快照，遇到断口重读，跨 DO 不声称原子快照。临时回执分片保存，客户端成功处理后显式释放；业务幂等身份与完整结果仍在 Agent。A–Worker 不设置 ACK 到期重传或周期待发扫描。

本地测试及短时平台冒烟不替代第 6 节要求的 24 小时受控 namespace 指标。测试和部署的实际结果、源码提交、Worker 版本及剩余限制均记录于 TEST_REPORT；未测量的 duration 和节费不填估算为实测。
