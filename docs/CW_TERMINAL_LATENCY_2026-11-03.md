# 线上 Terminal 响应耗时分析 · 2026-11-03

[文档索引](README.md) · [工作台实现](CW_WORKBENCH.md) · [刷新分析](CW_REFRESH_PERFORMANCE_2026-11-03.md)

修改前结论：Terminal 使用通用异步 HTTP 请求轮询。秒级 HTTP / 鉴权 / 转发成本被重复支付，再叠加输出轮询间隔和输入串行等待，因此难以实时交互。仅缩短网页定时器无法解决主要瓶颈。本文测量及源码分析均描述该旧版本；后续流式实现见文末。

## 线上只读测量

目标为 `https://r.xlogic.cc`，使用现有真实 Access 邮箱身份，正常续期 CoC 登录并恢复已有主机授权；项目仅选择此前明确记录的已结束测试会话所属项目。未打开 Shell、发送输入、接管会话、重启服务或更改运行配置。

| 样本 | Terminal POST → 202 | 首次结果查询，pending | 等待后第二次查询，completed | 结果可用总耗时 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 1,749 ms | 1,579 ms | 1,546 ms | 5,126 ms |
| 2 | 1,880 ms | 1,725 ms | 1,594 ms | 5,449 ms |
| 3 | 1,575 ms | 1,557 ms | 1,687 ms | 5,069 ms |

两次查询之间实际等待约 250 ms。三个健康接口请求仅 201–220 ms；另测身份接口 `/auth/me` 为 1,196 / 1,236 ms，主机列表为 4,077 / 3,326 ms。身份接口与 Terminal 使用的角色和查询内容不同，这些只是基线，不能直接相减当作 Terminal 的精确鉴权分段。

上表测量的是 `terminal/info`，证明同一路径的请求 / 回执成本，不代表真实按键回显实测值；read/input 还需验证活动 writer 和 control proof。没有服务器端同请求 trace，因此暂不能量化网络、D1、HostRelayDO 与 Agent 各自占比。健康接口没有同等业务校验，其速度不能代表完整浏览器至 Agent 的 RTT。

回收结果的 POST 另耗时 1,556–2,489 ms；上表总耗时不含回收。测量脚本等待回收以便控制并发，实际网页是异步发出回收，不阻塞结果返回。可公开的无凭证样本见 [measurement.json](assets/cw-terminal-latency-2026-11-03/measurement.json)。仅有三个 Terminal 样本，不作为 p95 或稳定 SLO。

## 源码解释

1. [terminal.tsx](../apps/web/src/workbench/terminal.tsx) 的输入每 100 ms 合并一次；`sending` 为 true 时不能再发，直到通用 `api()` 完整拿到结果。即便 Agent 早已执行输入，后续字符仍可能等待回执查询。xterm 不做本地字符回显，必须等远端 PTY 返回实际输出。
2. 输出调用 `queryApi(read)`，结果返回后再等待 500 ms 才开始下一次读取；只有 `more=true` 才立即继续。不是每 500 ms 就能看到一次新输出，而是“完整读取耗时 + 500 ms”一个周期。按当前 info 基线类比，可达约 5.6–5.9 秒；这是推算，不是 read 实测。
3. [api.ts](../apps/web/src/api.ts) 将 202 转为 operation 查询：立即查一次，pending 后按 250 / 500 / 1,000 / 2,000 ms 间隔退避，每个 GET 又是完整 HTTP 请求。输入和输出各自经过这条链；一次操作至少 POST + GET，完成后还要回收 POST。
4. [host.ts](../apps/relay/src/host.ts) 将 Terminal 控制操作归类为 transient。`complete()` 保存内存结果后直接返回，不调用 `changed()`。网页虽然监听通知通道，这类完成结果也不会主动通知它；仍靠轮询兜底发现。不能将已有 WebSocket 等同于 Terminal 已在推送输出。
5. [index.ts](../apps/relay/src/index.ts) 对 Terminal 和回执接口均重新调用 `authenticate()`；[common.ts](../apps/relay/src/common.ts) 的当前 D1 路径读取迁移标记，再由 RegistryCore 验证身份、邮箱授权及主机状态。非 info 的 Terminal 命令还会验证租约和 writer。源码和基线表明鉴权 / 状态读取值得优先追踪，但本轮没有取得其独立服务器计时，不将全部 1.5 秒归因于 D1。
6. [terminal.cpp](../native/src/terminal.cpp) 的 PTY 输出使用 `async_read_some` 收入内存缓冲，read 请求立即取当时已有内容，没有等待下一份输出的机制。200 ms 定时器用于进程退出 / 空闲检查，不是输出采集周期；不能把它误当主要输出延迟。

按键回显的路径是：输入合并 → HTTP 转发至 Agent → PTY 回显 → 等到下一次 read 覆盖这份输出 → HTTP 查询拿到内容 → xterm 绘制。读写会并行，不能简单把两次 info 总耗时相加就宣称每个字符固定延迟十秒；但持续输入确实被每批输入的完整确认串行限制。

## 优化顺序与实施边界

| 优先级 | 方案 | 预期作用与范围 |
| --- | --- | --- |
| P0 | 为同一请求关联 Worker 鉴权、D1/Registry、Host 转发、Agent 收发、结果查询耗时；不记录输入及输出正文 | 先确认秒级开销在哪一段。涉及 Relay 观测与受控线上采样；不能靠前端耗时猜区域或数据库放置 |
| P1 | 网页输入合并改为约 10–20 ms；Enter / Ctrl-C 优先冲刷；收到输入确认后触发一次合并的输出读取，正常有输出时立即续读 | 网页可缓解额外等待。保持单序列发送、offset 和取消代次约束，不直接并发发送相同 seq；收益受秒级 HTTP 成本限制 |
| P1 | 有界等待结果后直接返回确认；read 等待新 PTY 数据或超时，输出到达即返回，断开可取消 | 减少 202 + 多次 GET 及空轮询。需要 Relay / Agent 支持，仍保持 HTTP；先验证平台连接时限、取消和背压，避免长期挂起无限等待 |
| P2 | 为 Terminal 建立独立持续双向通道，推荐专用 WebSocket；open/close 保留现有可靠操作，输入/resize/output 在受控流中传输 | 消除每批字节反复发 HTTP / 查询结果的成本，接近单次网络往返回显。需要网页、协议、Relay 和 Agent 改动，不能只改 xterm |

P2 必须保留身份及 control 代次、项目隔离、撤销 / 到期关闭、输入 seq/确认、输出 offset/缺口、有界缓冲及背压。断线不自动重放无法确认的按键；新连接不能继承旧运行时的未知输入。通道建立后不能只验证一次身份便永久免检。现有通知 WebSocket 仍是通知通道，新增字节流须有明确新契约，不把业务正文偷塞进通知或云端持久化。

不建议仅把 500 ms 调成 10 ms：在当前链路下仍有秒级请求开销，同时增加空读、鉴权和数据库负载。也不建议用本地假回显掩盖延迟，会破坏密码输入、光标控制及全屏程序语义。

后续验收应在独立空闲测试项目中实测单字符回显、Enter、Ctrl-C、连续输入和持续输出的 p50/p95，并覆盖断线、撤权、背压与未知写入；记录输入发出、PTY 接收 / 输出、浏览器绘制的相关时间。可先以稳定网络下 p95 约 300 ms 或接近一至两个实测端到端 RTT 为设计目标，是否可达须实施后验证。本轮只有分析与文档，没有修改或部署 Terminal 实现。

## 全流式部署后的线上实测

用户授权后，在生产 `https://r.xlogic.cc` 测试已部署源码 `de93dc7`、Worker `9938aa32-193b-4f8f-9753-58a2889239f3` 与配套本机 Agent。正常邮箱登录，新建独立临时项目与普通 Web 会话，实际打开隔离 Bash PTY；未接管既有控制权、未调用模型。原始登录态和现场日志留在 ignored `.local/`，公开数据见 [online-latency.json](assets/cw-terminal-stream-2026-11-03/online-latency.json)。

结论：流式链路正常工作，但这条生产链路仍有秒级响应，尚未达到实时终端体验，不能沿用本地 115–165 ms 样本说明线上性能。首次创建会话至 Terminal 元数据就绪约 22.91 秒，点击打开至流式连接成功约 8.89 秒；这两项与持续交互分开计量。

| 操作 | 有效样本 | 最小 | 样本中位数 | 样本 P95 | 最大 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 单字符回显 | 19 | 976 ms | 1,878 ms | 2,429 ms | 2,429 ms |
| Enter → printf 结果标记 | 10 | 1,500 ms | 2,701 ms | 3,055 ms | 3,055 ms |

Ctrl-C 中断 `sleep 10` 至出现 `^C` 为 2,113 ms（单次）；以 100 ms 间隔产生 20 行输出，Enter 至首行 2,938 ms，首行后末行约 2,308 ms（包含预期约 1.9 秒的 Shell 输出间隔及自动化等待误差，不是纯传输耗时）。

计时在浏览器内以真实 keydown 开始，以 MutationObserver 观察 xterm DOM 出现预期内容结束，不把 Playwright 等待返回耗时计入逐键 / 命令结果；这仍不是物理屏幕绘制时间。共输入 20 个字符，第一个搜索目标与 Bash 提示符有重合可能，作为预热排除；表中仅使用后 19 个字符。命令以 Enter 为起点，输入行可能仍有前一批 ACK 等待，属于实际输入队列体验。样本量较少，P95 使用最近秩，不能作为稳定 SLO；临时项目独立，但主机及网络后台负载未隔离。旧版 info 基线与本轮真实按键的操作不同，不能据此计算严格加速倍数。

### 下一步优化依据

没有同一请求的服务器分段 trace，本次不能断言全部延迟来自 D1 或具体地域。源码可确认：输入仍只允许一批等待严格 ACK，连续输入及 Enter 可能排在前一批确认之后；Relay 每帧执行准备 / 身份检查，Terminal 又检查 Agent 身份与 writer/control，输出转发再次检查目标身份；身份缓存约 5 秒，未命中会查询 Registry。Host 热租约存储是 DO storage，不能将这些检查直接描述为每帧读取 D1。

优先在不记录 Shell 正文的条件下关联浏览器发送、Relay 排队 / 缓存命中与鉴权、Agent 接收 / PTY 输出、Relay 返回及浏览器渲染计时。然后评估有界输入窗口，保持序号顺序、未知输入不重放，并减少重复鉴权和事务读取：控制权代次及撤销仍须权威生效，不能简单永久跳过校验。首次创建 / 打开使用的可靠 HTTP 路径需单独减少回执往返；这些是后续建议，本轮没有再修改或部署实现。

## 第二轮：浏览器分段与对照分析

用户要求继续定位后，保持生产实现不变，再建两个独立临时项目 / 会话，采集 WebSocket send、输入 ACK、output 接收及 DOM 更新的同一浏览器时钟。每个单字符测试开始前明确等待上一批输入 ACK，排除已有输入积压；命令仍模拟打字后按 Enter。两轮合计 18 个字符、6 条命令及 6 次流式 ping；两个测试终端、会话、项目及空目录最终均确认清理。脱敏逐样本结果见 [latency-breakdown.json](assets/cw-terminal-stream-2026-11-03/latency-breakdown.json)。

### 已确认的时间构成

下表取首轮分段测试的代表样本，三段可相加；“远端整段”同时包含网络、Relay、Agent / PTY 等，不能直接称为纯网络 RTT。

| 样本 | 按键 → WebSocket 发出 | 发出 → 输出到达 | 到达 → DOM 更新 | 总计 |
| --- | ---: | ---: | ---: | ---: |
| 无前序输入积压的普通字符 | 6.2 ms | 977.4 ms | 6.4 ms | 990.0 ms |
| 无前序输入积压的慢字符 | 6.2 ms | 3,220.4 ms | 12.1 ms | 3,238.7 ms |
| 前序输入尚未确认时按 Enter | 3,087.9 ms | 981.3 ms | 12.4 ms | 4,081.6 ms |

首轮 12 次已清空前序 ACK 的字符：按键至实际发送 5.6–18.8 ms，最后输出到达至 DOM 更新 3.1–13.9 ms；多数输入 ACK 在发送后约 741–811 ms 返回，慢样本约 2.5–3.2 秒。由此可排除“xterm 绘制耗掉数秒”作为本次样本的主要解释。16 ms 合并定时器也不是普通字符的秒级主因；但网页一次只允许一批等待 ACK，实际命令样本中两次 Enter 的发送前等待分别为 2.89 / 3.09 秒，是已经测到的独立瓶颈。

流式 ping 仍经过 Terminal 的控制检查和 Agent，但不向 PTY 写入、不经过 Shell 执行和 xterm 绘制。6 次实际往返为 747.2 / 749.8 / 755.6 / 775.2 / 1,941.0 / 3,215.2 ms（此处排序展示）。因此约 0.75 秒的常见通道往返和秒级尖峰并非 Shell 单独造成；取消网页输入排队之后，也不能保证逐键回显降到数百毫秒。

### 已有线索及尚未证明的原因

1. **输入窗口是已确认的放大因素。** `terminal.tsx` 的 sending 直到 `TerminalStream.write()` 获得 ACK 才清除，新字符 / Enter 留在内存队列。浏览器时间戳已经直接测到数秒发送前等待；不需要用网络猜测解释这一段。
2. **网络路径有明显底座。** 只读内核 TCP 快照显示本机 Agent 当前 TLS 连接 RTT 约 234.7 ms，历史最小约 228.0 ms。这仅是 Agent 到其 TCP 对端的链路，不能将其当完整 browser → Relay → Agent RTT，也不能据此确定 DO 或 D1 地域。浏览器和 Agent 都在本机，结果也不能代表用户其它网络。
3. **ACK 后的小包等待值得做对照。** 多个普通字符的输入 ACK 比其输出早约 225–235 ms，与 Agent TCP RTT 接近；共享 `socket_impl.hpp` 连续独立 async_write ACK 和 output，未显式配置 TCP_NODELAY。Nagle / TCP 确认等待是候选解释，也可能含远端逐帧处理 / 路由等待；没有切换该选项的 A/B，不能宣称已经证明。即便确认并消除约 230 ms，它也无法单独解决数秒尖峰。
4. **周期鉴权仍是候选尖峰来源。** 不经过 Shell 的 ping 也有 1.94 / 3.22 秒样本，源码中的身份缓存 5 秒到期后会调用 Registry，Agent / 客户端按各自身份检查。此轮没有对应的服务器分段日志，尚不能把每个慢样本匹配为缓存未命中，不能将全部尖峰归因于 D1。

尝试读取现有 `host_frame` / `registry_call` 指标，无需部署观测代码。Wrangler Tail 遭遇本机直连 DNS / 网络错误，用户先前提供的 localhost:10809 代理也未成功建立 TLS；通过保留 TLS 校验的替代连接可达 API，但 Tail 连接仍被重置。本轮没有取得可用的服务器分段日志，不编造 Relay / D1 / Agent 的时间占比。探测仅影响诊断进程，未修改系统 DNS、生产路由或服务配置。

### 实施建议与顺序

| 优先级 | 改动 / 验证 | 能解决的问题及边界 |
| --- | --- | --- |
| P0 | 将单批输入等待 ACK 改为有界多批窗口，seq 顺序分配，累计 / 逐批确认，未确认字节及批数设上限，resize 可合并；未知输入仍不重放 | 直接消除已测得的 2.9–3.1 秒前序确认等待；不会消除单键自己的通道往返。不能改为无限并发或跳过顺序验证 |
| P0 | 增加受控 Terminal 计时：Relay 收到 / 排队完成 / 身份检查完成 / 发给 Agent，Agent 收到 / PTY 写入 / 输出 / 发回，Relay 收到 / 发给浏览器；关联 seq / offset，不记正文 | 区分常见约 0.75–1 秒底座与周期尖峰。分别记录授权命中 / 未命中、队列深度及耗时；不同机器时钟不直接相减 |
| P1 | 对共享 TCP 传输的 TCP_NODELAY 做真实高 RTT A/B，覆盖 TLS / plain 和重连 | 验证 ACK 后约一段 RTT 的输出延迟是否为小包等待，收益按实测给出；需原生升级，不能靠网页定时器修复 |
| P1 | 根据服务器计时减少重复鉴权 / 热路径事务，使用有期限的身份缓存合并并发刷新、实时撤销失效及本地控制代次校验 | 只在日志确认后调整。继续保留到期、撤销、Agent epoch、writer/control 校验及背压，不将一次握手变成永久免检 |
| P2 | 若健康、通道与服务器计时确认主要是跨地域链路，再评估 Host DO / Registry / D1 放置及 Agent 到边缘路径 | 当前没有地理定位证据，不建议先迁移数据库或改变权威状态来源 |

本轮完成分析与文档，没有修改或再次部署网页、Relay、协议或原生实现。
