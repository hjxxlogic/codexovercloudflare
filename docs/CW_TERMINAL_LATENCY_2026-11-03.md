# 线上 Terminal 响应耗时分析 · 2026-11-03

[文档索引](README.md) · [工作台实现](CW_WORKBENCH.md) · [刷新分析](CW_REFRESH_PERFORMANCE_2026-11-03.md)

修改前结论：Terminal 使用通用异步 HTTP 请求轮询。秒级 HTTP / 鉴权 / 转发成本被重复支付，再叠加输出轮询间隔和输入串行等待，因此难以实时交互。仅缩短网页定时器无法解决主要瓶颈。本文测量及源码分析均描述该旧版本；后续流式实现见文末。

## 线上只读测量

目标为 `https://r.xlogic.cc`，使用现有真实 Access 邮箱身份，正常续期 CoC 登录并恢复已有主机授权；项目仅选择此前明确记录的已结束测试会话所属项目。未打开 Shell、发送输入、接管会话、重启服务或更改运行配置。

| 样本 | Terminal POST → 202 | 首次结果查询，pending | 等待后第二次查询，completed | 结果可用总耗时 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 1,749 ms | 1,579 ms | 1,546 ms | 5,126 ms |
| 2 | 1,880 ms | 1,725 ms | 1,594 ms | 5,449 ms |
| 3 | 1,575 ms | 1,557 ms | 1,687 ms | 5,069 ms |

两次查询之间实际等待约 250 ms。三个健康接口请求仅 201–220 ms；另测身份接口 `/auth/me` 为 1,196 / 1,236 ms，主机列表为 4,077 / 3,326 ms。身份接口与 Terminal 使用的角色和查询内容不同，这些只是基线，不能直接相减当作 Terminal 的精确鉴权分段。

上表测量的是 `terminal/info`，证明同一路径的请求 / 回执成本，不代表真实按键回显实测值；read/input 还需验证活动 writer 和 control proof。没有服务器端同请求 trace，因此暂不能量化网络、D1、HostRelayDO 与 Agent 各自占比。健康接口没有同等业务校验，其速度不能代表完整浏览器至 Agent 的 RTT。

回收结果的 POST 另耗时 1,556–2,489 ms；上表总耗时不含回收。测量脚本等待回收以便控制并发，实际网页是异步发出回收，不阻塞结果返回。可公开的无凭证样本见 [measurement.json](assets/cw-terminal-latency-2026-11-03/measurement.json)。仅有三个 Terminal 样本，不作为 p95 或稳定 SLO。

## 源码解释

1. [terminal.tsx](../apps/web/src/workbench/terminal.tsx) 的输入每 100 ms 合并一次；`sending` 为 true 时不能再发，直到通用 `api()` 完整拿到结果。即便 Agent 早已执行输入，后续字符仍可能等待回执查询。xterm 不做本地字符回显，必须等远端 PTY 返回实际输出。
2. 输出调用 `queryApi(read)`，结果返回后再等待 500 ms 才开始下一次读取；只有 `more=true` 才立即继续。不是每 500 ms 就能看到一次新输出，而是“完整读取耗时 + 500 ms”一个周期。按当前 info 基线类比，可达约 5.6–5.9 秒；这是推算，不是 read 实测。
3. [api.ts](../apps/web/src/api.ts) 将 202 转为 operation 查询：立即查一次，pending 后按 250 / 500 / 1,000 / 2,000 ms 间隔退避，每个 GET 又是完整 HTTP 请求。输入和输出各自经过这条链；一次操作至少 POST + GET，完成后还要回收 POST。
4. [host.ts](../apps/relay/src/host.ts) 将 Terminal 控制操作归类为 transient。`complete()` 保存内存结果后直接返回，不调用 `changed()`。网页虽然监听通知通道，这类完成结果也不会主动通知它；仍靠轮询兜底发现。不能将已有 WebSocket 等同于 Terminal 已在推送输出。
5. [index.ts](../apps/relay/src/index.ts) 对 Terminal 和回执接口均重新调用 `authenticate()`；[common.ts](../apps/relay/src/common.ts) 的当前 D1 路径读取迁移标记，再由 RegistryCore 验证身份、邮箱授权及主机状态。非 info 的 Terminal 命令还会验证租约和 writer。源码和基线表明鉴权 / 状态读取值得优先追踪，但本轮没有取得其独立服务器计时，不将全部 1.5 秒归因于 D1。
6. [terminal.cpp](../native/src/terminal.cpp) 的 PTY 输出使用 `async_read_some` 收入内存缓冲，read 请求立即取当时已有内容，没有等待下一份输出的机制。200 ms 定时器用于进程退出 / 空闲检查，不是输出采集周期；不能把它误当主要输出延迟。

按键回显的路径是：输入合并 → HTTP 转发至 Agent → PTY 回显 → 等到下一次 read 覆盖这份输出 → HTTP 查询拿到内容 → xterm 绘制。读写会并行，不能简单把两次 info 总耗时相加就宣称每个字符固定延迟十秒；但持续输入确实被每批输入的完整确认串行限制。

## 优化顺序与实施边界

| 优先级 | 方案 | 预期作用与范围 |
| --- | --- | --- |
| P0 | 为同一请求关联 Worker 鉴权、D1/Registry、Host 转发、Agent 收发、结果查询耗时；不记录输入及输出正文 | 先确认秒级开销在哪一段。涉及 Relay 观测与受控线上采样；不能靠前端耗时猜区域或数据库放置 |
| P1 | 网页输入合并改为约 10–20 ms；Enter / Ctrl-C 优先冲刷；收到输入确认后触发一次合并的输出读取，正常有输出时立即续读 | 网页可缓解额外等待。保持单序列发送、offset 和取消代次约束，不直接并发发送相同 seq；收益受秒级 HTTP 成本限制 |
| P1 | 有界等待结果后直接返回确认；read 等待新 PTY 数据或超时，输出到达即返回，断开可取消 | 减少 202 + 多次 GET 及空轮询。需要 Relay / Agent 支持，仍保持 HTTP；先验证平台连接时限、取消和背压，避免长期挂起无限等待 |
| P2 | 为 Terminal 建立独立持续双向通道，推荐专用 WebSocket；open/close 保留现有可靠操作，输入/resize/output 在受控流中传输 | 消除每批字节反复发 HTTP / 查询结果的成本，接近单次网络往返回显。需要网页、协议、Relay 和 Agent 改动，不能只改 xterm |

P2 必须保留身份及 control 代次、项目隔离、撤销 / 到期关闭、输入 seq/确认、输出 offset/缺口、有界缓冲及背压。断线不自动重放无法确认的按键；新连接不能继承旧运行时的未知输入。通道建立后不能只验证一次身份便永久免检。现有通知 WebSocket 仍是通知通道，新增字节流须有明确新契约，不把业务正文偷塞进通知或云端持久化。

不建议仅把 500 ms 调成 10 ms：在当前链路下仍有秒级请求开销，同时增加空读、鉴权和数据库负载。也不建议用本地假回显掩盖延迟，会破坏密码输入、光标控制及全屏程序语义。

后续验收应在独立空闲测试项目中实测单字符回显、Enter、Ctrl-C、连续输入和持续输出的 p50/p95，并覆盖断线、撤权、背压与未知写入；记录输入发出、PTY 接收 / 输出、浏览器绘制的相关时间。可先以稳定网络下 p95 约 300 ms 或接近一至两个实测端到端 RTT 为设计目标，是否可达须实施后验证。本轮只有分析与文档，没有修改或部署 Terminal 实现。
